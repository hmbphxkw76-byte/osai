## 1. 架构原则

### 1.1 原生框架优先（最高优先级）

| 规则 | 编号 | 说明 |
|------|------|------|
| 原生 API 直接使用 | **G-001** | 各子项目优先使用其原生框架提供的 API（PyRIT / garak），不自造轮子 |
| 混合方案优先 | **G-002** | 原生不完全支持时，优先继承/包装/组合原生组件进行增强 |
| 纯自研兜底 | **G-003** | 仅当原生框架完全无法实现该功能时，方可纯自研模块 |

**禁止事项**：
- 禁止原生可用时自研替代
- 禁止覆盖原生框架核心生命周期（如 `scenario.run_async()`）
- 自研模块必须至少组合或依赖一个原生组件

### 1.2 项目独立性

| 规则 | 编号 | 说明 |
|------|------|------|
| 物理隔离 | **G-004** | `pyrit-pipeline/`、`garak-pipeline/`、`ai-recon-core/` 三者目录独立，互不引用对方业务代码 |
| 共享层单向依赖 | **G-005** | `ai-recon-core` 是共享基础库，不依赖 `pyrit` 也不依赖 `garak`；两个 pipeline 通过 exporter 消费共享层 |
| 源码不可修改 | **G-006** | `src/` 目录下的上游框架源码（PyRIT / garak）禁止修改，扩展通过继承或封装实现 |

### 1.3 数据驱动决策

| 规则 | 编号 | 说明 |
|------|------|------|
| 攻击效果优先 | **G-007** | 攻击效果（ASR 提升）是第一优先级，优先于代码美观、覆盖率、性能等次要指标 |
| ASR 数据驱动 | **G-008** | 所有攻击策略选择、场景路由、技术组合优先级以 ASR 实测数据为核心驱动指标 |
| 攻击为王 | **G-009** | 当攻击效果与代码质量冲突时，优先保证攻击效果，再补技术债 |

## 2. 代码质量与 L5 专家标准

### 2.1 L5 专家水平基准

所有代码改动必须以 **100% 对齐 L5 专家水平** 为目标，覆盖以下维度：

| 维度 | 标准 |
|------|------|
| **攻击面覆盖** | OWASP LLM Top 10 + Agentic Security (ASI01-ASI10) 全覆盖；攻击链组合完整（编码绕过 + 翻译 + 角色扮演等 Buff 叠加） |
| **评估严谨性** | 评分器经过校准，ASR 数据可信，报告包含 DEFCON 评分、置信区间、攻击成功率 |
| **代码规范** | 类型注解、docstring（Google 风格）、异常处理完备 |
| **可追溯性** | 输出报告可追溯，证据链完整 |

### 2.2 代码风格

| 规则 | 编号 | 说明 |
|------|------|------|
| 类型注解 | **G-010** | 所有公共函数/方法必须有类型注解 |
| docstring | **G-011** | 所有公共类/方法必须有 Google 风格 docstring |
| 日志 | **G-012** | 使用 `logging` 而非 `print` 进行调试输出 |
| 行长度 | **G-013** | 行长度 ≤ 120 字符（pyrit-pipeline）/ ≤ 88 字符（garak-pipeline 遵循上游） |
| lint | **G-014** | 所有代码改动后必须通过 `ruff` 检查，零新增错误 |

### 2.3 OWASP 分类标准

| 规则 | 编号 | 说明 |
|------|------|------|
| OWASP ID 为唯一键 | **G-015** | OWASP LLM Top 10 (LLM01-LLM10) + Agentic Security (ASI01-ASI10) 作为统一分类键 |
| 优先级排序 | **G-016** | Probe/Scenario 按 Tier 优先级排序（Tier1 > Tier2 > Tier3 > 其他） |

## 3. 分级测试策略

### 3.1 强制规则

> **G-017**：代码改动后必须按改动范围执行对应级别的测试。未执行对应级别测试的改动不得提交。测试失败必须修复后再继续。

### 3.2 三级测试体系

| 级别 | 触发条件 | 测试范围 | 命令 |
|------|----------|----------|------|
| **单元测试** | 单模块内改动 | 该模块的 `test_*.py` | `python -m pytest tests/test_<module_name>.py -v` |
| **集成测试** | 模块之间交互改动 | 跨模块数据传递和状态流转 | `python -m pytest tests/test_integration.py -v` |
| **回归测试** | 多个模块同时修改 | 全部测试 | `python -m pytest tests/ -v` |

### 3.3 测试覆盖要求

| 规则 | 编号 | 说明 |
|------|------|------|
| 正常路径 | **G-018** | 覆盖所有正常执行路径 |
| 边界条件 | **G-019** | 覆盖边界值、空输入、极限值 |
| 异常路径 | **G-020** | 覆盖异常输入、网络失败、超时等错误场景 |
| 测试命名 | **G-021** | 测试文件命名：`tests/test_<module_name>.py` |

### 3.4 覆盖率要求

| 规则 | 编号 | 说明 |
|------|------|------|
| 最低覆盖率 | **G-022** | 代码覆盖率 ≥ 75%（pyrit-pipeline 硬性要求） |
| 关键路径 | **G-023** | 核心攻击链路、评分器、数据导出路径必须有测试覆盖 |

## 4. 代码改动前置流程

### 4.1 L5 差距分析报告（强制）

> **G-024**：每次方案进行优化、调整、重构或修复后（无论大小），在动手修改代码之前必须执行以下流程。

**四步流程**：

| 步骤 | 内容 |
|------|------|
| **1. 方案概述** | 清晰描述本次优化/调整后的完整技术方案（做了什么、为什么、预期效果） |
| **2. L5 差距分析** | 以 L5 专家水准为基准，客观分析当前方案与 100% 对齐 L5 之间的差距，至少覆盖：攻击面完整性、评估严谨性、工程健壮性、代码质量 |
| **3. 完整解决方案** | 针对每项差距，给出可落地的完整修复方案（含具体文件、方法、实施步骤） |
| **4. 用户确认** | 上述三步产出必须先呈现给用户，等待明确确认后再执行代码修改 |

**例外**（可跳过确认流程）：
- 纯文档/注释纠错
- 记忆库更新
- 用户已显式要求"立即实现/直接改"的指令

### 4.2 改动影响评估

| 规则 | 编号 | 说明 |
|------|------|------|
| 改动前评估 | **G-025** | 修改任何文件前，先评估对其他模块/项目的潜在影响 |
| 跨项目审查 | **G-026** | 修改 `ai-recon-core` 时，必须检查对 `pyrit-pipeline` 和 `garak-pipeline` 的影响 |

## 5. 研究资料优先级

### 5.1 理论先行原则

> **G-027**：在面临新技术、新方法、新概念时，资料调研须按以下优先级顺序进行，不得跳级。

| 优先级 | 来源 | 说明 |
|--------|------|------|
| **1** | **学术文献（arxiv.org）** | 首选阅读预印本论文与正式发表文献，确保有理论基础；引用时须标注 arXiv 编号与标题 |
| **2** | **官方权威源码库（GitHub）** | 参考 PyRIT、garak、Microsoft AI Red Team 等官方仓库的高 star 项目 |
| **3** | **自行搜索** | 仅当前两级无法找到可靠资料时兜底使用，须交叉验证来源可信度 |

**理由**：AI 安全红队评估高度依赖前沿研究，理论先行确保方法论严谨性，避免凭直觉或碎片化博客做决策。

## 6. 项目隔离与目录边界

### 6.1 项目职责边界

| 项目 | 职责 | 依赖 |
|------|------|------|
| `recon-pipeline/` | 共享侦察能力（认证、探针、统一数据模型、导出器） | 无框架依赖 |
| `pyrit-pipeline/` | 基于 PyRIT 的攻击流水线 | `import pyrit` + `import recon_pipeline` |
| `garak-pipeline/` | 基于 Garak 的攻击流水线 | `import garak` + `import recon_pipeline` |

### 6.2 代码归属判断

| 你的代码做什么？ | 放哪里？ | 判断依据 |
|---|---|---|
| 目标侦察（端点探测、模型指纹、MCP/RAG/Agent 接口发现） | `recon-pipeline/` | 两个 pipeline 共享的基础能力 |
| 依赖 `import garak` 的逻辑 | `garak-pipeline/` | 框架专属，不应出现在其他项目 |
| 依赖 `import pyrit` 的逻辑 | `pyrit-pipeline/` | 框架专属，不应出现在其他项目 |
| 不依赖任何框架的基础能力（只服务于一个 pipeline） | 对应 pipeline 的 `pipeline/` | 非共享能力 |
| 格式导出器（ReconReport → Garak/PyRIT 格式） | `recon-pipeline/exporters/` | 桥接共享层与下游 |

### 6.3 目录结构约定

| 规则 | 编号 | 说明 |
|------|------|------|
| 入口文件 | **G-028** | 每个子项目必须有 `main.py` 作为入口，且 `main.py` 必须是纯编排（不包含业务逻辑） |
| 业务逻辑 | **G-029** | 所有业务逻辑必须在 `pipeline/` 目录内 |
| 配置文件 | **G-030** | 配置文件统一放在 `config/` 目录 |
| 输出产物 | **G-031** | 运行输出统一放在 `outputs/` 目录，由 `.gitignore` 忽略 |

## 7. 版本控制与 Git 规范

### 7.1 Commit Message 格式

> **G-050**：所有 commit message 必须遵循 Conventional Commits 规范。

格式：`<type>(<scope>): <description>`

| type | 说明 | 示例 |
|------|------|------|
| `feat` | 新功能 | `feat(pipeline): add multimodal probe routing` |
| `fix` | Bug 修复 | `fix(asr): correct score normalization edge case` |
| `refactor` | 重构（不改变功能） | `refactor(scenarios): extract scoring to composite` |
| `test` | 测试相关 | `test(converters): add modality router unit tests` |
| `docs` | 文档更新 | `docs(rules): add CI/CD section to global rules` |
| `chore` | 构建/工具/依赖 | `chore(deps): bump pyrit to 1.0.2` |
| `perf` | 性能优化 | `perf(export): batch evidence writes` |
| `style` | 代码风格（不影响逻辑） | `style(pipeline): fix ruff E501 violations` |
| `ci` | CI/CD 变更 | `ci(github): add pytest workflow` |

### 7.2 分支策略

| 规则 | 编号 | 说明 |
|------|------|------|
| 主分支保护 | **G-051** | `main` 分支永远处于可部署状态，禁止直接推送 |
| 功能分支 | **G-052** | 新功能在 `feat/<描述>` 分支开发，合并前必须通过 CI |
| 修复分支 | **G-053** | Bug 修复在 `fix/<描述>` 分支开发 |
| 合并方式 | **G-054** | 优先使用 squash merge，保持 `main` 历史干净 |

### 7.3 .gitignore 规范

| 规则 | 编号 | 说明 |
|------|------|------|
| 产物隔离 | **G-055** | `outputs/`、`*.pyc`、`__pycache__/`、`.pytest_cache/`、`*.egg-info/`、`.venv/` 必须加入 `.gitignore` |
| 凭证保护 | **G-056** | 包含密钥/Token 的配置文件（`.env`、`*secret*`）必须加入 `.gitignore` |
| 大型文件 | **G-057** | 数据集、模型文件等大型二进制资产不入库，通过清单文件（YAML）声明来源 |

## 9. 运行时环境规范

### 9.1 临时文件清理

> **G-032**：每次 Pipeline 运行前和运行后，必须自动清理 Python 临时文件。禁止跳过清理步骤。

| 清理对象 | 说明 | 清理时机 |
|----------|------|----------|
| `__pycache__/` | Python 字节码缓存目录 | 运行前 + 运行后 |
| `*.pyc`、`*.pyo` | 编译字节码文件 | 运行前 + 运行后 |
| `.pytest_cache/` | pytest 测试缓存目录 | 运行前 + 运行后 |

- **运行前清理**：移除过期字节码和测试缓存，确保干净起点，避免 stale bytecode 导致难以调试的问题
- **运行后清理**：移除本次运行生成的临时缓存，保持环境整洁
- **保留**：`outputs/` 目录下的报告文件保留供人工审查，不受清理影响

> 注意：`.pytest_cache/` 已加入 `.gitignore`，不会被提交到版本控制，但运行时仍需主动清理以避免缓存干扰。

### 9.2 网络容错

| 规则 | 编号 | 说明 |
|------|------|------|
| 镜像容错 | **G-033** | HuggingFace 等外部服务不可达时，自动回退到国内镜像（hf-mirror.com） |
| 用户选择优先 | **G-034** | 如果用户已显式设置环境变量（如 `HF_ENDPOINT`），尊重用户选择，不覆盖 |
| 降级策略 | **G-035** | 镜像不可达时打印警告，继续执行（使用本地缓存） |

### 9.3 速率控制

| 规则 | 编号 | 说明 |
|------|------|------|
| 慢启动 | **G-036** | 扫描使用慢启动策略（初始低并发，逐步提升） |
| 随机抖动 | **G-037** | 每次 API 调用前加随机抖动延迟，打破规律时间指纹 |
| 限流降速 | **G-038** | 检测到 429 限流自动降速，无 429 后渐进恢复 |

## 11. 工程健壮性

| 规则 | 编号 | 说明 |

### 11.3 配置管理

| 规则 | 编号 | 说明 |
|------|------|------|
| 配置分离 | **G-048** | 配置与代码分离，通过 YAML 文件管理 |

## 12. API 设计与接口稳定性

### 12.1 向后兼容

| 规则 | 编号 | 说明 |
|------|------|------|
| 公开 API 稳定 | **G-066** | 公共函数/类的签名变更必须保持向后兼容，或在下一个大版本中废弃 |
| 语义化版本 | **G-067** | 遵循 SemVer：MAJOR.MINOR.PATCH，破坏性变更必须升 MAJOR |
| 弃用警告 | **G-068** | 废弃公开 API 前必须至少保留一个 MINOR 版本并发出 `DeprecationWarning` |

### 12.2 接口设计原则

| 规则 | 编号 | 说明 |
|------|------|------|
| 开闭原则 | **G-069** | 对扩展开放、对修改关闭：通过继承/组合扩展功能，不修改已有稳定代码 |
| 依赖倒置 | **G-070** | 高层模块不依赖低层模块，两者都依赖抽象（ABC / Protocol） |
| 接口隔离 | **G-071** | 不强迫客户端依赖它不使用的方法，大接口拆分为小接口 |
| 显式优于隐式 | **G-072** | 参数显式传递，避免隐式全局状态 |

### 12.3 命名规范

| 规则 | 编号 | 说明 |
|------|------|------|
| 模块命名 | **G-073** | 模块名使用 `snake_case`（`stage_scenario.py`），类名使用 `PascalCase`（`StageScenario`） |
| 函数命名 | **G-074** | 函数/方法使用 `snake_case`，动词开头（`build_attack_list`、`export_report`） |
| 常量命名 | **G-075** | 常量使用 `UPPER_SNAKE_CASE`（`MAX_RETRIES`、`DEFAULT_TIMEOUT`） |
| 私有成员 | **G-076** | 模块内部/类内部使用的函数和变量以单下划线 `_` 前缀标记 |
| 避免缩写 | **G-077** | 除非是行业通用缩写（ASR、HTTP、JSON），否则禁止使用缩写命名 |
| 布尔命名 | **G-078** | 布尔变量/函数以 `is_`、`has_`、`can_`、`should_` 前缀（`is_authenticated`、`has_mcp_server`） |

## 13. 性能与资源管理

### 13.1 资源释放

| 规则 | 编号 | 说明 |
|------|------|------|
| 上下文管理器 | **G-079** | 文件、网络连接、数据库连接等必须使用 `with` 语句或显式 `close()` |
| 异步清理 | **G-080** | 异步资源（Playwright Browser、aiohttp Session）必须 `await` 关闭，禁止直接 `del` |
| 内存管理 | **G-081** | 大数据集优先使用生成器/迭代器流式处理；但需权衡可读性，简单场景不强制 |

### 13.2 性能优化原则

| 规则 | 编号 | 说明 |
|------|------|------|
| 可读性优先 | **G-082** | 代码可读性优先于微优化；通过 profiling 定位实际瓶颈后再针对性优化 |
| 批量操作 | **G-083** | 网络请求、文件写入等 I/O 操作优先批量处理，减少往返次数 |
| 缓存策略 | **G-084** | 昂贵计算结果（如模型指纹、ASR 统计数据）应缓存并设置 TTL |

### 13.3 并发规范

| 规则 | 编号 | 说明 |
|------|------|------|
| async/await 一致性 | **G-085** | 异步函数必须带 `async` 后缀或文档说明；禁止在 async 函数中调用同步阻塞 I/O |
| 并发控制 | **G-086** | 使用 `asyncio.Semaphore` 控制并发数，避免打爆目标 API |
| 线程安全 | **G-087** | 多线程共享数据使用 `threading.Lock` 或 `queue.Queue` |

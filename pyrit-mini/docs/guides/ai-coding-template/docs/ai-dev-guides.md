# AI 编程通用规范框架 — Universal AI-Coding Spec Framework

> **文档定位**：跨模型、跨项目的 AI 辅助编程**规范与流程**框架模板。适用于任何使用 AI 进行软件开发的项目。
> **核心理念**：通过**规范分层金字塔（Spec Pyramid）** + **开发三元组机制** + **质量关卡（Gate Stages）** + **跨模型一致性政策**，根治 Vibe Coding 的五大根因，达到生产级（L5 目标）标准。
> **适用范围**：个人项目、团队协作、企业级系统、开源基础设施、跨模型协作。
> **文档家族**：本文件是**规范与流程（Normative + Process）** 单一事实源；验证与度量（Verification + Measurement）见同目录 `ai-dev-audit.md`。两者共享术语表见本文档附录 D。
> **如何使用本模板**：将全文 `${...}` 占位符替换为你的项目实际值（阶段名、目录、命令、红线）。结构可直接复制到任意新项目。
> **合规标准**：对齐 L5 专家水准 + 跨模型一致性协议 + 生产级工具链。
> **版本**：v5.0（2026-09-12）— 解耦项目细节、拆分"规范分层/审计成熟度"概念、统一门禁术语、补 Spec-as-Code 与可观测性。

## 第一部分：规范分层金字塔（Spec Pyramid）

> 本金字塔描述**要编写哪些规范文档（artifacts）**，与 `ai-dev-audit.md` 的"审计成熟度 A0–A5"（描述验证有多严）是**两个不同维度**，切勿混淆。

### 1.1 什么是"规范分层金字塔"？

```
                    ▲
                   /  \
                  / L0 \           ← 宪法 (Constitution)
                 /______\             最高约束：使命 / 裁决序 / 红线
                /   L1    \        ← 蓝图 (Architecture)
               /____________\          技术架构 / 模块边界 / 数据契约
              /     L2      \       ← 需求 (Requirements)
             /________________\         做什么 / 验收标准 / 负需求
            /       L3        \     ← 任务 (Tasks)
           /____________________\       怎么做 / 粒度限制 / task-spec
          /         L4          \    ← 护栏 (Guardrails)
         /__________________________\    红线 / 质量关卡 / 防御层
```

**"黄金"的含义**：

| 特性 | 说明 |
|------|------|
| **稳定性** | 5 层结构提供足够治理粒度，既不过简也不过繁 |
| **可复用性** | 骨架适用于任何 AI 编程项目——只需替换每层内容 |
| **层次清晰** | 上层约束下层，下层支撑上层，消除规则冲突 |
| **可验证性** | 每一层都有对应检查器与验收标准（Spec-as-Code，见 §1.7） |
| **跨模型中立** | 定义"规范骨架"，不绑定任何具体模型 |

### 1.2 设计原则

| 原则 | 说明 | 违反后果 |
|------|------|---------|
| **上约下** | 上层规则约束下层，下层不得违抗上层 | 规则冲突、AI 无所适从 |
| **下撑上** | 下层实现支撑上层目标，不得架空上层 | 规范成为空文 |
| **层间约束** | 金字塔稳定来自层间约束，而非单层复杂度 | 单层过载、整体失衡 |
| **裁决有序** | 层间冲突有明确裁决优先级 | 规则战争 |
| **粒度递减** | L0 最抽象，L4 最具体（检查器/关卡） | 混乱不分层 |

### 1.3 裁决序（Priority of Authority）

```
① 宪法 (L0)        ← 最高约束，不可违抗
② 蓝图 (L1)        ← 技术架构决策
③ 需求 (L2)        ← 做什么、验收标准
④ 任务 (L3)        ← 怎么做、范围限制
⑤ 护栏 (L4)        ← 红线（安全部分视同宪法级）
⑥ 用户即时指令     ← 仅通过合法通道生效
⑦ AI 自由裁量      ← 默认权限为零
```

**裁决规则**：
1. **合法通道原则**：⑥ 与 ①–⑤ 冲突时，AI 不得直接执行，必须走"修正案 / 规格变更 / 新任务"三通道之一。
2. **红线升级原则**：L4 护栏中的**安全红线**视同宪法级——安全不因架构/需求让路。
3. **零权限原则**：⑦ 任何未在前五层登记的行为都需要 L3 任务规格的明确授权。
4. **冲突处理原则**：高层级无条件压倒低层级；同层级冲突走变更提案流程。

### 1.4 五大根因与五层的对应

| # | 根因 | 症状 | 后果 | 解决层 |
|---|------|------|------|--------|
| 1 | **规则无裁决序** | AI 不知道听谁的 | 同一功能多种实现 | **L0 宪法** |
| 2 | **做什么无规格** | AI 自由发挥 | 核心功能被破坏 | **L2 需求** |
| 3 | **任务粒度失控** | 修 Bug 变重构 | 30 行→3000 行 | **L3 任务** |
| 4 | **双轨未被禁止** | 同名功能多实现 | 同一逻辑 3 版本 | **L1 蓝图** |
| 5 | **汇报不透明** | "已验证"但跑不通 | stub 进主干 | **L4 护栏** |

### 1.5 与传统"规范文档"的区别

| 维度 | 传统规范文档 | 规范分层金字塔 |
|------|------------|---------------|
| **结构** | 扁平"大杂烩" | 5 层，层间有约束关系 |
| **裁决** | 靠"常识" | 明确序位 ①>②>…>⑦ |
| **验证** | 人工 review，标准模糊 | 每层有检查器（Spec-as-Code） |
| **可复用** | 强绑定特定项目 | 骨架通用，内容可替换 |
| **防跑偏** | 依赖 AI"理解力" | 依赖结构化"硬约束" |
| **跨模型** | 无定义 | 有完整一致性协议 |

### 1.6 层间交互矩阵

| 来自↓ \ 影响到→ | L0 | L1 | L2 | L3 | L4 |
|----------------|---|---|---|---|---|
| **L0** | — | 约束原则 | 质量目标 | 工作流原则 | 红线来源 |
| **L1** | 支撑落地 | — | 架构约束 | 模块边界 | 工具链依赖 |
| **L2** | 验收依据 | 能力要求 | — | 任务来源 | 测试标准 |
| **L3** | 执行记录 | 变更请求 | 状态更新 | — | 触发条件 |
| **L4** | 违宪拦截 | 不变量守护 | 质量保障 | 完成门槛 | — |

### 1.7 关键增强：Spec-as-Code（规范即代码）

> **L5 必备**：纯散文规范无法被机器校验，是"规范漂移"的根源。每条可机械化判定的规则必须同时有**可执行检查器**。

- **L0 红线** → 至少一个 guard 检查器（`check_red_line_*(...)`），BLOCKING 自动阻断。
- **L1 数据契约** → 字段读写校验器（`contract_validator`）。
- **L2 验收标准** → 至少一条自动化测试或可判定断言。
- **L3 粒度上限** → pre-commit 检查（文件数 / diff 行数 / 跨模块数）。
- **L4 门禁** → 关卡脚本（见 §5）。

> 规范文件本身纳入版本控制，与代码同仓库、同门禁、同 review。

## 第二部分：5 分钟快速入门

> **目标**：按以下 4 步即可拥有 MVP 级别的生产级规范。命令以 `python` 为例，Windows 可用 `py` 替代；`${GUARD_CMD}` 等占位符见 §5.1。

### Step 1：填写一句话使命（2 分钟）

创建 `00-CONSTITUTION.md`：

```markdown
# 00 — [项目名称] 宪法

## 第 0 条：项目使命
对 [什么用户/场景]，[提供什么能力]，以 [核心指标] 为首要度量。
```

**示例**：
> 对移动端用户，提供高并发购物车管理能力，以**数据一致性**为首要度量。

### Step 2：定义三条红线（2 分钟）

```markdown
## 三条红线
- 禁止：[最严重的 1 类问题] — BLOCKING
- 禁止：[最严重的 2 类问题] — BLOCKING
- 禁止：[最严重的 3 类问题] — BLOCKING
```

**示例**：
- 禁止：支付流程跳过风控检查 — BLOCKING
- 禁止：用户数据跨租户混用 — BLOCKING
- 禁止：数据库事务中执行外部 HTTP 调用 — WARNING

### Step 3：设置一个验证步骤（1 分钟）

```markdown
## 验证步骤（至少选一个）
- [ ] 静态检查：${LINT_CMD}
- [ ] 单元测试：${TEST_CMD}
- [ ] 类型检查：${TYPECHECK_CMD}
- [ ] 构建验证：${BUILD_CMD}
```

### Step 4：创建 backlog.md（30 秒）

```markdown
# backlog（唯一待办池）

| ID | 问题 | 发现时间 | 状态 |
|----|------|---------|------|
| BL-01 | [发现的非本任务问题] | YYYY-MM-DD | 冻结 |
```

### 完成！✅

你现在有了 MVP 级别规范体系：宪法（使命+红线）+ 验证步骤 + 待办池。

**下一步**：运行 1–2 周后，根据实际痛点再决定是否扩展为完整五层。

## 第三部分：开发工作流

> **核心机制**：将开发全生命周期拆为三个不可绕过的检查点 + 八个执行步骤。

### 3.1 开发三元组（防跑偏核心）

```
┌──────────────────────────────────────────────────────────────────┐
│                      开发三元组（开发全审）                        │
│  ┌──────────────┐   ┌──────────────┐   ┌──────────────┐        │
│  │  开发前      │   │  开发中      │   │  开发后      │        │
│  │  开发必看    │→│  开发必跑    │→│  开发必验    │        │
│  │  = 规范      │   │  = 验证      │   │  = 交付      │        │
│  │  查看文档    │   │  跑关卡      │   │  跑验收清单  │        │
│  └──────────────┘   └──────────────┘   └──────────────┘        │
│  超级别名："开发全审" = "开发三元组" = 必看+必跑+必验 全部三阶段 │
└──────────────────────────────────────────────────────────────────┘
```

### 3.2 八步执行协议

```
Step 1: 宪法自检 ─┐
Step 2: 蓝图落点 ─┤ 开发必看（规范）
Step 3: 需求关联 ─┤
Step 4: 文件清单 ─┘
Step 5: 粒度自检 ─┐
                  ├ 实施编码
Step 6: 实施编码 ─┘
Step 7: 质量关卡 ── 开发必跑（验证）+ 可选跨模型审查
Step 8: 汇报验收 ── 开发必验（交付）
```

### 3.3 开发前：开发必看

| 必看内容 | 文档位置 | 必须回答的问题 |
|---------|---------|---------------|
| 宪法 | `00-CONSTITUTION.md` | 最不能违反的规则是什么？ |
| 蓝图 | `10-ARCHITECTURE.md` | 模块在哪个层级？依赖谁？ |
| 需求 | `20-REQUIREMENTS.md` | 验收标准是什么？ |
| 红线 | `40-GUARDRAILS.md` | 哪些代码模式绝对禁止？ |

### 3.4 开发中：开发必跑（质量关卡 Gate Stages）

> ⚠️ 术语区分：**质量关卡 = 阶段序列（本文件）**；**问题等级 = BLOCKING/WARNING/INFO（见 `ai-dev-audit.md`）**。

**基础版（个人/小项目）**：

| 步 | 命令 | 通过标准 |
|----|------|---------|
| 1 | `${LINT_CMD}` | 0 违规 |
| 2 | `${TEST_CMD}` | 0 失败 |

**生产版（团队/企业）**：

| 步 | 命令 | 通过标准 | 拦截什么 |
|----|------|---------|---------|
| 1 | `${GUARD_CMD}` | 0 新增 BLOCKING | 架构/红线违规 |
| 2 | `${LINT_CMD}` | 0 违规 | 风格/导入/未用变量 |
| 3 | `${TEST_CMD}` | 0 失败 | 功能回归 |
| 4 | `${DRYRUN_CMD}` | 无 ImportError/AttributeError | 数据流断点 |
| 5 | `${DRIFT_CMD}` | 0 BLOCKING | 规范漂移 |
| 6 | `${DATAFLOW_CMD}` | 0 失败 | 契约违例 |

**跨模型版（多模型协作）**：在上述基础上增加第 7 步 `${CROSSMODEL_CMD}`（一致性度量，协议见 `ai-dev-audit.md` §5）。

**不同技术栈命令示例**（占位符在 §5.1 统一定义）：

| 技术栈 | `${GUARD_CMD}` | `${LINT_CMD}` | `${TEST_CMD}` |
|--------|--------------|-------------|-------------|
| **Python** | `python -m tools.guard` | `ruff check . --fix` | `pytest tests/ -v` |
| **JavaScript/TS** | `node guard.js` | `eslint . --fix` | `jest --passWithNoTests` |
| **Go** | `go vet ./...` | `golangci-lint run` | `go test ./...` |
| **Java** | `mvn validate` | `mvn checkstyle:check` | `mvn test` |
| **Rust** | `cargo clippy` | `cargo clippy --fix` | `cargo test` |

### 3.5 开发后：开发必验（交付验收清单）

```markdown
# 交付验收清单：TASK-___

## 一、规格符合性
- [ ] 代码改动范围 = 任务规格文件清单
- [ ] 无清单外文件被修改
- [ ] diff 行数 ≤ ${DIFF_LIMIT}（默认 300）

## 二、架构合规
- [ ] guard：0 新增 BLOCKING / 0 新增 WARNING
- [ ] 红线：0 违例
- [ ] 不变量：未被破坏

## 三、测试覆盖
- [ ] 新增/修改代码有对应测试
- [ ] 全部测试通过

## 四、流水线验证
- [ ] dry-run 无异常
- [ ] drift 检测 0 BLOCKING
- [ ] 数据流完整性测试通过

## 五、跨模型一致性（如适用）
- [ ] 跨模型评审已执行
- [ ] 一致性度量达标（见 ai-dev-audit.md §5）

## 六、文档同步
- [ ] 相关 specs 已更新
- [ ] backlog 已更新
- [ ] 版本号已递增

## 七、三栏汇报
- ✅ 已完成并验证：[改动点 → 门禁证据]
- ⚠️ 已完成但未验证：[差集及理由]
- ❌ 未完成：[显式列出及原因]

验收人：___ 日期：___
```

### 3.6 会话入口仪式与收尾义务

**入口仪式**（每次会话开始）：
1. 读宪法 — 确认核心条款未被遗忘
2. 查路线图领任务 — 确认当前任务 = 序列中下一个
3. 读蓝图相关章节 — 声明：模块落点 / 依赖方向 / 上下文字段
4. 核对 REQ 验收标准 — 抄入 task-spec
5. 填写 task-spec — 粒度自检（文件≤3 / diff≤${DIFF_LIMIT} / 模块≤2）
6. **计划复述** — **3–5 句话复述：改什么、怎么改、为什么满足验收标准**
7. 跨模型判断（如适用）

**Step 6 是防偏航关键闸门**：复述偏差会被当场纠正，成本最低。跳过直接编码 = 违宪。

**收尾义务**（每次会话结束）：
1. **三栏汇报**：✅已完成并验证 / ⚠️已完成未验证 / ❌未完成
2. **状态表回填**：更新需求状态
3. **backlog 增量登记**：发现的非本任务问题 → BL-xxx
4. **审查归档**（如有跨模型审查）

### 3.7 STOP-REPORT 熔断机制

**触发信号**（出现任一即停）：

| # | 信号 | 对应条款 |
|---|------|---------|
| 1 | 需修改 task-spec 之外的文件 | C4 |
| 2 | 规格与代码现实不符 | C6 |
| 3 | 新增依赖/字段但规格未授权 | C4/C7 |
| 4 | 超出粒度上限（文件>3 / diff>${DIFF_LIMIT}） | C4 |
| 5 | 实现路径会触碰红线 | R-S |
| 6 | 无法判断核心指标升降 | C2 |
| 7 | 跨模型审查发现重大分歧（κ<0.4） | C14 |

**STOP-REPORT 格式**：

```markdown
## STOP-REPORT
- 触发条款: C4/C11/C14
- 现状: （一句话）
- 矛盾: 规格说 X / 代码现实是 Y
- 选项:
  A. 修改任务规格，纳入新范围
  B. 缩小当前任务，新发现登记 backlog
  C. 中止任务
- 建议: B（理由）
```

### 3.8 会话上下文管理协议

> **P0 优先级**：解决长会话中 AI"遗忘"核心规则的问题。

#### 3.8.1 会话决策日志

| 字段 | 内容 | 示例 |
|------|------|------|
| timestamp | ISO8601 | `2026-09-12T14:32:00+08:00` |
| decision | 决策摘要 | "选择方案 B：使用枚举替代字符串常量" |
| rationale | 决策理由 | "符合 C3 SSOT 原则，避免双轨" |
| specs_ref | 依据条款 | C3, R-H3 |
| impact_level | 影响范围 | high/medium/low |

#### 3.8.2 上下文分层管理

```
┌──────────────────────────────────────────┐
│  L1 核心宪法（必须全量保留）              │
│  + 使命 / 红线 / 核心条款                │
├──────────────────────────────────────────┤
│  L2 当前任务上下文（选择性加载）          │
│  + 当前 task-spec / 相关 REQ / 涉及模块  │
├──────────────────────────────────────────┤
│  L3 项目背景知识（摘要形式保留）          │
│  + 架构摘要 / 债务清单 / 最近 3 次决策   │
├──────────────────────────────────────────┤
│  L4 历史对话（可压缩/丢弃）              │
│  + 超过 N 轮前的对话内容                 │
└──────────────────────────────────────────┘
```

#### 3.8.3 Checkpoint 协议

**触发时机**：每完成一个 task-spec / 会话超 30 分钟 / 即将切换子任务。

```markdown
## Checkpoint [HH:MM]
- 已完成：[task 编号 + 一句话结果]
- 待完成：[剩余工作]
- 关键决策：[本次会话的核心决策摘要]
- 风险标记：[遗留问题 / 未验证项]
```

#### 3.8.4 会话溢出预防

| 指标 | 预警阈值 | 动作 |
|------|---------|------|
| 上下文 token 占用 | >70% 上限 | 主动压缩 L4 历史 |
| 单次会话 task 数 | >3 个 | 强制 checkpoint |
| 漂移事件数 | >2 次 | 强制宪法重载 |
| 连续 WARNING | >5 条 | 暂停，人工确认 |

#### 3.8.5 会话恢复检查清单

1. [ ] 读取最近一次 Checkpoint
2. [ ] 还原 L1 核心宪法上下文
3. [ ] 验证 L2 任务上下文与当前任务一致
4. [ ] 检查 L3 是否有未解决的 debt

### 3.9 代码所有权标注规范

> **P1 优先级**：清晰标注 AI 生成/辅助人类修订的代码，支撑审计与责任追溯。

| 标注类型 | 格式 | 示例 |
|---------|------|------|
| **AI-GENERATED** | 文件级头部注释 | `# [AI-GENERATED] via ${MODEL} | 2026-09-12 | TASK-042` |
| **AI-ASSISTED** | 行级内联注释 | `result = validate(x)  # [AI-ASSISTED] 异常边界检查建议` |
| **AI-REVIEWED** | commit message 后缀 | `feat: TASK-042 新增导出功能 [AI-REVIEWED]` |
| **AI-TESTED** | 测试文件标注 | `# [AI-TESTED] 测试用例由模型生成，人工确认通过` |

**规则**：机器可解析；禁止删除已有标注（除非代码完全重写且不再含 AI 生成内容）。

### 3.10 紧急修复豁免流程

> **P1 优先级**：平衡紧急情况下的快速响应与规范遵守。

**豁免触发条件**（任一）：P0 故障 / 安全漏洞正在被攻击 / 合规硬性截止。

**豁免流程**：触发 → 即时报备 Tech Lead → 执行修复（可简化门禁）→ 48h 内补全豁免记录 → 人工复盘 → 更新规范（如需）。

**豁免纪律**：
- 每年最多 3 次（超出升级工程负责人）
- 不得用于规避架构/安全红线
- 48h 内未完成补全 → 记入债务
- 重复出现的"紧急"模式应转化为常规流程

### 3.11 DoD（Definition of Done，L5 必备）

> 任务"完成"的唯一客观判据，所有关卡通过后仍须满足：

- [ ] 三栏汇报中无 ❌，⚠️ 项有显式理由
- [ ] 所有 BLOCKING/WARNING 已修复或经白名单豁免（有审批+过期日）
- [ ] 门禁全绿（基础版至少 lint+test；生产版 6 步）
- [ ] 关联 REQ 状态已更新，diff 关联 task ID
- [ ] 可复现：使用的模型版本 / prompt 版本已记录（见 §5.8）

## 第四部分：L0–L4 各层级详述

### 4.0 L0：宪法（Constitution）

**定义**：AI 编码行为的最高约束。回答：项目为什么存在？冲突时谁说了算？AI 不能做什么？何时必须停？

#### 核心条款清单

| 条款 | 名称 | 描述 | 判定标准 |
|------|------|------|---------|
| **C1** | 原生优先 | 写代码前先检索是否现成能力 | 新类与已有功能重叠 → 违例 |
| **C2** | 核心质量至上 | 任何变更不得降低核心质量属性 | diff 中出现降级行为 → 违例 |
| **C3** | 单一事实源(SSOT) | 一个概念只能一个实现 | 新增文件职责重叠 → 违例 |
| **C4** | 最小变更 | 只改任务规格列出的文件 | diff 出现清单外文件 → 违例 |
| **C5** | 先读后写 | 修改前必须先完整读取文件 | 编辑无前置读取 → 违例 |
| **C6** | 规格先行 | 无任务规格不编码 | diff 无法关联 task ID → 违例 |
| **C7** | 配置数据流 | 所有参数走唯一配置链路 | 硬编码参数 → 违例 |
| **C8** | 引用留痕 | 每个非显然决策有引用注释 | 新引入技术无引用 → 违例 |
| **C9** | 诚实汇报 | 显式区分三态 | "完成"无验证证据 → 违例（证据造假） |
| **C10** | 验证义务 | 每次变更后关卡全部执行 | 门禁未全过即标记完成 → 违例 |
| **C11** | 停止权 | 含糊/矛盾/超权限时 STOP-REPORT | 以上情形继续编码 → 违例 |
| **C12** | 修正案协议 | 宪法自身只通过修正案变更 | 未经流程直接改宪法 → 违例 |
| **C13** | 跨模型等价（政策） | 同任务不同模型结果应等价 | 输出相似度 r < 0.85 → 触发复核（度量见 audit §5） |
| **C14** | 多模型协议优先 | 跨模型分歧以协议裁决为准 | 未经仲裁自行覆盖 → 违例 |

> **C13 说明**：r（Pearson）衡量**输出相似度**；跨模型审查的**结论一致度**用 Cohen's κ（见 `ai-dev-audit.md` §5）。二者不可互换。

### 4.1 L1：蓝图（Architecture）

**定义**：系统目标架构、模块边界、数据契约与架构不变量。

**通用分层结构**（按项目替换目录名）：

| 层 | 职责 | 规则 |
|----|------|------|
| **编排层** | 入口 + 流程编排 | 不得含业务逻辑 |
| **核心层** | 配置解析 + 上下文 | 禁止带 `__main__` |
| **阶段层** | 各功能阶段实现 | 彼此只通过上下文交接 |
| **工具层** | CLI 开发/运维工具 | 所有 `__main__` 必须在此 |
| **支撑层** | 终端展示、日志 | 单向依赖核心层 |
| **数据层** | 声明式资产 | 只读，不含代码 |

**硬规则**：
1. 阶段层模块间**只准通过上下文字段交接数据**，禁止直接 import
2. 上下文对象是唯一被全员依赖的枢纽
3. 循环导入合法解法：函数内延迟导入 / TYPE_CHECKING / 合并

**数据契约模板**：

```markdown
## 上下文对象字段契约
| 字段 | 唯一写者 | 读者 | 类型 | 约束 |
|------|---------|------|------|------|
| `${field_a}` | 阶段 X | 阶段 Y, Z | dict | not_empty |

## 数据传递规则
| 规则 | 说明 |
|------|------|
| X→Y | `${field_a}` 非空 + `${field_b}` 非空 |
```

### 4.2 L2：需求（Requirements）

**定义**：所有"做什么"的唯一登记处。**未登记的需求 = 不存在**。

**需求分级**：P0 主链路（变更需 change-proposal+评审）/ P1 支撑（规格变更）/ P2 体验（普通任务）。

**负需求（禁止清单）示例**：

```markdown
| ID | 禁止事项 | 理由 |
|----|---------|------|
| NEG-1 | 禁止扩展双轨/债务 | SSOT |
| NEG-2 | 禁止核心链路添加降级逻辑 | 核心质量至上 |
| NEG-3 | 禁止绕过数据契约新开通道 | 架构约束 |
| NEG-4 | 禁止引入新运行时依赖（提案制） | 供应链安全 |
```

### 4.3 L3：任务（Tasks）

**粒度上限**：

| 维度 | 上限 | 超限处理 |
|------|------|---------|
| 文件数 | ≤3 | 先拆分 |
| diff 行数 | ≤${DIFF_LIMIT}（默认 300） | 先拆分 |
| 跨模块数 | ≤2 | 先拆分 |
| 新增文件 | ≤1 | 先拆分 |

> **黄金法则**：觉得"顺手把那个也改了"——STOP，记入 backlog。

**task-spec 模板**见附录 A.4。

### 4.4 L4：护栏（Guardrails）

**定义**：定义"别越线"——红线绝对禁止，关卡是完成任务必要条件。

**红线分类**：

| 类别 | 级别 | 检查方式 | 后果 |
|------|------|---------|------|
| **机器红线 (R-L)** | BLOCKING | guard 自动检查 | 阻断 commit/push |
| **人工红线 (R-H)** | WARNING | diff 评审 | 评审驳回 |
| **安全红线 (R-S)** | BLOCKING | 人工评审 | 最严重违例 |
| **跨模型红线 (R-CROSS)** | WARNING | 跨模型审查 | 升级仲裁 |

> 问题等级（BLOCKING/WARNING/INFO）的完整定义与处置流程见 `ai-dev-audit.md` §4。

**通用红线清单（按需启用检查器）**：

| # | 红线名称 | 检查器 |
|---|---------|--------|
| R-L1 | 业务逻辑红线（项目自定义） | `check_red_line_1()` |
| R-L2 | 自定义基类替代框架原生 | `check_native_first()` |
| R-H1 | 静默降级：stub/空实现进主干 | `check_stub()` |
| R-H2 | 静默吞错：`except: pass` | `check_bare_except()` |
| R-H3 | 双轨新增：职责重叠 | `check_dual_track()` |
| R-H4 | 配置断点：硬编码参数 | `check_hardcoded()` |
| R-H5 | 数据旁路：绕过契约新开通道 | `check_data_bypass()` |
| R-H6 | 规格蒸发：diff 无法关联需求 | `check_spec_link()` |
| R-H7 | 证据注水：汇报未实际验证 | `check_verification()` |

### 4.5 安全威胁模型（L4.5，P0）

> 所有安全相关规范的顶层设计，适用于任何 AI 编程项目。详细检测规则与响应流程见 `ai-dev-audit.md` §6（安全审计维度）；此处定义**红线政策**。

**安全红线（政策级）**：

| 红线 ID | 名称 | 判定标准 | 级别 |
|---------|------|---------|------|
| **R-SEC-01** | 禁止未净化外部输入参与代码执行 | eval/exec/compile 用户输入 | BLOCKING |
| **R-SEC-02** | 禁止生成含系统命令调用代码（未授权） | os.system/subprocess 未授权 | BLOCKING |
| **R-SEC-03** | 禁止输出含 PII / API 密钥 / 凭证 | 正则匹配泄露模式 | BLOCKING |
| **R-SEC-04** | 禁止推荐有已知 CVE 的依赖版本 | 依赖漏洞扫描违例 | BLOCKING |
| **R-SEC-05** | 禁止绕过已定义安全检查函数 | 重写/跳过/禁用 guard | BLOCKING |
| **R-SEC-06** | 敏感操作必须有审计日志 | 无日志记录高危操作 | WARNING |
| **R-SEC-07** | 依赖更新需通过安全扫描 | 直接引入未扫描依赖 | WARNING |

**Prompt Injection 识别特征**（输入层防护）：指令伪装成数据 / 角色扮演绕过 / 编码混淆绕过 / 间接注入 / 渐进式诱导。

**依赖供应链检查（政策）**：版本锁定 + hash 校验（BLOCKING）、已知 CVE 扫描（BLOCKING）、官方仓库+签名（BLOCKING）、许可证兼容（WARNING）。

## 第五部分：自动化工具链集成

### 5.1 占位符统一定义（模板契约）

> 在任何新项目中，先在 `audit_config.yaml`（或等价文件）绑定这些占位符到真实命令，文档其余部分即可原样复用。

| 占位符 | 含义 | Python 示例 |
|--------|------|------------|
| `${GUARD_CMD}` | 静态架构/红线检查 | `python -m tools.guard` |
| `${LINT_CMD}` | 代码风格 | `ruff check . --fix` |
| `${TEST_CMD}` | 单元测试 | `pytest tests/ -v` |
| `${TYPECHECK_CMD}` | 类型检查 | `mypy src` |
| `${DRYRUN_CMD}` | 运行时 dry-run | `python main.py --dry-run` |
| `${DRIFT_CMD}` | 规范漂移检测 | `python -m tools.drift_detector --full` |
| `${DATAFLOW_CMD}` | 数据流契约测试 | `pytest tests/test_data_flow.py` |
| `${CROSSMODEL_CMD}` | 跨模型一致性度量 | `python -m tools.cross_model_check` |
| `${WATCH_CMD}` | 实时监听 | `python -m tools.watch` |
| `${INSTALL_HOOKS_CMD}` | hooks 安装 | `python tools/install_hooks.py` |
| `${DIFF_LIMIT}` | diff 行数上限 | `300` |

> ⚠️ 通用化：`py` 是 Windows 启动器；跨平台模板统一用 `python`（Windows 用户可别名 `py`）。

### 5.2 Git Hooks 模板（通用骨架）

```bash
#!/bin/sh
# .git/hooks/pre-commit
echo "Running pre-commit checks..."
if ! ${GUARD_CMD} > /dev/null 2>&1; then echo "[BLOCK] guard failed."; exit 1; fi
if ! ${LINT_CMD} > /dev/null 2>&1; then echo "[BLOCK] lint failed."; exit 1; fi
if ! ${QUICKCHECK_CMD} --staged > /dev/null 2>&1; then echo "[BLOCK] quick check failed."; exit 1; fi
echo "[PASS] All pre-commit checks passed."; exit 0
```

```bash
#!/bin/sh
# .git/hooks/pre-push
echo "Running pre-push checks..."
if ! ${TEST_CMD} > /dev/null 2>&1; then echo "[BLOCK] tests failed."; exit 1; fi
if ! ${DRIFT_CMD} > /dev/null 2>&1; then echo "[BLOCK] drift detected."; exit 1; fi
# 跨模型一致性为 WARNING，不阻断 push
${CROSSMODEL_CMD} || echo "[WARN] cross-model issues found."
echo "[PASS] pre-push checks passed."; exit 0
```

> 实际命令脚本需项目自行实现（guard/lint/test 等），本框架只规定**关卡顺序与阻断语义**，不绑定具体工具。

### 5.3 测试策略

| 测试类型 | 覆盖目标 | 门禁阶段 |
|---------|---------|---------|
| 单元测试 | 每个函数/方法 | 基础/生产 |
| 集成测试 | 模块间数据流 | 生产 |
| 契约测试 | 上下文字段读写 | 生产 |
| 回归测试 | 历史 bug 不复发 | 生产 |

**覆盖率目标**：

| 项目级别 | 行覆盖率 | 分支覆盖率 |
|---------|---------|-----------|
| P0 核心模块 | ≥90% | ≥80% |
| P1 支撑模块 | ≥75% | ≥60% |
| P2 辅助模块 | ≥50% | 不要求 |

### 5.4 实时检查与自动化

```bash
${WATCH_CMD}                 # 全量监听
${WATCH_CMD} --fast          # 仅修改文件
${WATCH_CMD} --package <pkg> # 监听特定包
${QUICKCHECK_CMD} path/file  # 单文件
${QUICKCHECK_CMD} --staged   # 已暂存
${INSTALL_HOOKS_CMD}         # 安装 hooks
```

### 5.5 可复现性治理（L5 必备）

> AI 编码结果依赖模型与 prompt 版本。必须钉死以保证可复现与可审计。

- 记录每次生成的 `${MODEL}` 版本（如 `claude-3.5-sonnet-20241022`）
- prompt / system 模板纳入版本控制，变更走 CHANGELOG
- 关键生成任务记录 `output_hash`（见 §5.8 日志）
- 禁止在未锁定模型版本的情况下将生成物合并入主干

### 5.6 AI 交互日志规范（政策 + 字段）

> 详细检测器实现与恢复流程见 `ai-dev-audit.md` §7（幻觉检测维度）。此处定义**日志字段契约**，支撑审计与回溯。

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| timestamp | ISO8601 | ✅ | 精确到秒 |
| session_id | string | ✅ | 会话唯一标识 |
| model_id | string | ✅ | 使用的 AI 模型+版本 |
| interaction_type | enum | ✅ | generate/validate/refactor/review |
| input_summary | string(≤500) | ✅ | 输入摘要（不含敏感数据） |
| output_hash | string | ✅ | 输出 SHA256 |
| decision_outcome | enum | ✅ | accepted/revised/rejected |
| gate_result | enum | ✅ | pass/fail/warn |
| hallucination_flag | boolean | ✅ | 是否触发幻觉检测 |
| specs_references | string[] | ✅ | 涉及的规范条款 |
| drift_impact_score | float | 可选 | 对规范健康度影响分 |

## 第六部分：跨模型一致性政策

> **政策层（本文件）**定义"何时需要跨模型审查、谁来审、阈值政策"；**度量协议（κ/r 计算、仲裁、报告）** 见 `ai-dev-audit.md` §5，二者通过本政策引用。

### 6.1 问题背景

多模型协作中同任务可能产出不同结果。通过**协议化审查**将"主观分歧"转为"可量化差异"，再以分级仲裁解决。

### 6.2 模型注册表模板

```markdown
# 模型注册表
| 模型 ID | 提供商 | 版本 | 角色 | 偏差倾向 | 适用场景 |
|--------|--------|------|------|---------|---------|
| model_a | ${PROVIDER} | v1.0 | 主审查 | 保守 | ${SCENARIO} |
| model_b | ${PROVIDER} | v2.0 | 辅助审查 | 激进 | ${SCENARIO} |
| model_c | ${PROVIDER} | v1.5 | 仲裁 | 中性 | 分歧裁决 |
```

### 6.3 审查策略（政策阈值）

| 变更级别 | 审查模型数 | 一致性阈值 | 仲裁级别 |
|---------|-----------|-----------|---------|
| P0 核心 | 全部模型 | κ ≥ 0.75 | Tier 3 人工 |
| P1 支撑 | ≥2 个模型 | κ ≥ 0.60 | Tier 2 升级 |
| P2 辅助 | ≥1 个模型 | κ ≥ 0.50 | Tier 1 合并 |
| 文档 | 抽查 | — | — |

> **κ 与 r 的分工**（统一口径）：κ 衡量**多模型审查结论的一致度**（分类一致）；r 衡量**生成产物输出的相似度**（连续量）。阈值政策见上；计算方法见 `ai-dev-audit.md` §5.2–§5.3。

### 6.4 审查触发条件

| 条件 | 是否触发 |
|------|---------|
| P0 核心模块变更 | ✅ 必须 |
| 新增依赖 | ✅ 必须 |
| 安全相关变更 | ✅ 必须 |
| 跨地区/跨模型协作部署 | ✅ 必须 |
| P2 辅助优化 | ❌ 可选 |
| 文档更新 | ❌ 不需要 |

### 6.5 三级仲裁（政策）

| 级别 | 触发条件 | 仲裁方式 |
|------|---------|---------|
| **Tier 1** | κ ≥ 0.60 | 自动合并 |
| **Tier 2** | 0.40 ≤ κ < 0.60 | 升级第三方模型 |
| **Tier 3** | κ < 0.40 | 人工仲裁 |

### 6.6 已知模型偏差模式

| 偏差类型 | 描述 | 缓解 |
|---------|------|------|
| 保守偏差 | 倾向拒绝变更 | 设最低接受阈值 |
| 激进偏差 | 倾向接受变更 | 增加人工审核 |
| 风格偏差 | 代码风格偏好不同 | 以 lint 为准 |
| 框架偏差 | 特定框架偏好 | 以技术栈约束为准 |
| 安全偏差 | 安全严格度不同 | 以安全红线为准 |

## 第九部分：FAQ

### Q1：规范越多越好吗？
不是。规范应**刚好够用**。3 条能解决就不写 13 条；lint 够用就不需要 34 个检查器。

### Q2：AI 不遵守宪法怎么办？
纯文本约束易被忽略，需配套自动化检查器 + git hook + BLOCKING 阻断。

### Q3：规范会拖慢开发吗？
牺牲一点绝对速度，避免大量跑偏修复时间。初始稍慢、中期快、长期更快。

### Q4：规范和敏捷冲突吗？
不冲突。规范是交通规则，敏捷是目的地。

### Q5：如何让 AI"记住"宪法？
文件存在（可读取）+ 工具集成（guard 执行）+ 触发词（如"完整验证"）。

### Q6：规范需要定期更新吗？
需要。宪法走修正案；蓝图走变更流程；护栏按需调整。建议每月回顾。

### Q7：AI 产出"看起来对但实际错"怎么办？
不要信任"看起来对"；每个 API 调用验证（类型检查 + dry-run）；记录已知幻觉模式。

### Q8：如何判断是否需要完整八步协议？
改动 ≤50 行且非核心 → 简化（Step 4-5-7）；涉及核心/新模块/跨模型 → 完整八步 + 对应审查。

### Q9：跨模型审查成本如何控制？
分级执行：小修单模型抽查（低）；中改双模型（中）；重构/架构变更全模型+仲裁（高/极高）。仅 P0 与跨地区协作常态化。

### Q10：什么叫"达到 L5"？
见 `ai-dev-audit.md` §3「L5 达标清单」——可量化的客观判据（关卡全绿 + 跨模型 κ 达标 + 零 BLOCKING + 可复现 + 日志完整），而非主观宣称。

## 附录 L：规范推荐引擎

```python
def recommend_specs(profile: dict) -> list:
    base = ["L0 宪法", "L2 MVP 需求", "L3 任务"]
    if profile["size"] in ["大型", "巨型"]:
        base += ["L1 完整蓝图", "L4 完整护栏", "跨模型审查"]
    if "安全" in profile["core_quality"]:
        base += ["安全威胁模型", "依赖扫描", "Prompt Injection 防护"]
    if profile["compliance"]:
        base += ["审计日志", "数据分级", "合规检查器"]
    return base
```

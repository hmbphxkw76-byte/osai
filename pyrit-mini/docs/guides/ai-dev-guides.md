# AI 编程生产级规范指南

> **文档定位**：AI 辅助编程的通用规范框架，适用于任何使用 AI 进行软件开发的项目。
> **核心理念**：通过五层规约金字塔，将 AI 从"随机发散的代码生成器"转变为"可预测的规范执行者"。
> **适用范围**：个人项目、团队协作、企业级系统、开源基础设施。
> **版本**：v2.1（2026-09-09）

---

## ⚡ 5 分钟快速入门（完全新手）

如果你从未使用过 AI 编程规范，按以下 4 步即可拥有 **MVP 级别** 的生产级规范：

### Step 1：填写一句话使命（2 分钟）

复制下面的模板，填写你的项目信息：

```markdown
# 00 — [你的项目名称] 宪法

## 第 0 条：项目使命
[对什么用户/场景]，[提供什么能力]，以[核心指标]为首要度量。

示例：
# 00 — 电商购物车服务 宪法

## 第 0 条：项目使命
对移动端用户，提供高并发购物车管理能力，以数据一致性和可用性为首要度量。
```

### Step 2：定义三条红线（2 分钟）

选择对你项目最严重的 3 个禁止项：

```markdown
## 三条红线
- 禁止：[最严重的 1 类问题] — BLOCKING
- 禁止：[最严重的 2 类问题] — BLOCKING
- 禁止：[最严重的 3 类问题] — BLOCKING

示例：
## 三条红线
- 禁止：支付流程跳过风控检查 — BLOCKING
- 禁止：用户数据跨租户混用 — BLOCKING
- 禁止：数据库事务中执行外部 HTTP 调用 — WARNING
```

### Step 3：设置一个验证步骤（1 分钟）

每次代码变更后，至少执行以下一项：

```markdown
## 验证步骤（至少选一个）
- [ ] 静态检查：[你的 lint 命令，如 eslint / ruff check / golangci-lint]
- [ ] 单元测试：[你的测试命令，如 jest / pytest / go test]
- [ ] 类型检查：[你的类型检查命令，如 tsc --noEmit / mypy]
- [ ] 构建验证：[你的构建命令，如 npm build / go build]
```

### Step 4：创建一个待办池（30 秒）

```markdown
# backlog.md（唯一待办池）

| ID | 问题 | 发现时间 | 状态 |
|----|------|---------|------|
| BL-01 | [发现的非本任务问题] | 2026-09-09 | 冻结 |
```

### 完成！✅

你现在有了 MVP 级别的规范体系：
- ✅ 宪法（使命 + 红线）
- ✅ 验证步骤
- ✅ 待办池

**下一步**：运行 1-2 周后，根据实际痛点再决定是否扩展为完整五层（见第六部分 6.3 MVP）。

## 第一部分：核心理念与根因分析

### 1.1 什么是 Vibe Coding？

Vibe Coding（氛围编码）是指使用 AI 辅助编程时，通过自然语言描述需求，由 AI 生成代码的开发方式。它的优势是快速原型，但风险是**不可预测的跑偏**。

### 1.2 五大根因

| # | 根因 | 症状 | 后果 | 对应解决方案 |
|---|------|------|------|-------------|
| 1 | **规则无裁决序** | AI 不知道听谁的，随机选 | 同一功能多种实现，互相冲突 | L0 宪法 — 裁决序 |
| 2 | **做什么无规格** | AI 自由发挥，改 20 个文件 | 核心功能反而被破坏 | L2 需求 — 规格先行 |
| 3 | **任务粒度失控** | 修 Bug 变重写架构 | 30 行修复变 3000 行重构 | L3 任务 — 粒度上限 |
| 4 | **双轨未被禁止** | 同名功能多个实现 | ASR 计算有 3 个版本 | L1 蓝图 — SSOT |
| 5 | **汇报不透明** | "已验证"但跑不通 | stub 静默进主干 | L4 护栏 — 四步门禁 |

### 1.3 规范的价值主张

**没有规范**：AI 是"随机发散的代码生成器"——能做对，但不可预测。

**有规范**：AI 是"可预测的规范执行者"——不一定最快，但几乎不会跑偏。

```
                    速度
                    ↑
    有规范 + 快 ●   |   ● 无规范 + 快（但危险）
                    |
    ────────────────┼────────────────→ 可预测性
                    |
    有规范 + 稳 ●   |   ● 无规范 + 慢（混乱）
                    |
```

**核心权衡**：规范牺牲了一点"绝对速度"，换来了**可预测性**和**可维护性**。

### 1.4 何时不需要完整规范

| 场景 | 建议 |
|------|------|
| 一次性脚本（<100 行） | 只需 lint |
| 概念验证（<1 天） | 只需 lint + 手动验证 |
| 个人工具（仅自己用） | MVP 级别（第六部分 6.3） |
| 生产系统（多人/长期） | 完整五层 |

**反模式**：不要为了规范而规范。如果 3 条规则能解决问题，不要写 13 条。

## 第二部分：五层规约金字塔

### 2.1 金字塔结构

```
              ▲
             /  \
            / L0 \        ← 宪法（Constitution）：AI 行为的最高约束
           /______\          解决"规则无裁决序"
          /   L1    \     ← 蓝图（Architecture）：技术架构与模块边界
         /____________\       解决"双轨冗余"
        /     L2      \   ← 需求（Requirements）：做什么、验收标准
       /________________\     解决"做什么无规格"
      /       L3        \ ← 任务（Tasks）：怎么做、粒度限制
     /____________________\   解决"任务粒度失控"
    /         L4          \← 护栏（Guardrails）：红线、门禁、防线
   /__________________________\ 解决"汇报不透明"
```

**设计原则**：上层约束下层，下层支撑上层。金字塔的稳定来自于**层间约束**而非单层复杂度。

### 2.2 L0：宪法（Constitution）

#### 2.2.1 定义

宪法是 AI 编码行为的最高约束。它回答以下问题：
- 这个项目**为什么存在**？（使命）
- 规则冲突时**谁说了算**？（裁决序）
- AI **不能做什么**？（核心条款）
- 什么情况下 AI **必须停下来**？（停止权）

#### 2.2.2 裁决序（Priority of Authority）

```
① 本宪法
② 技术蓝图（Architecture）
③ 需求规格（Requirements）
④ 任务规格（Task Spec）
⑤ 护栏细则（Guardrails）
⑥ 用户即时指令
⑦ AI 自由裁量（默认权限为零）
```

**裁决规则**：
- ⑥ 只能通过合法通道生效：与 ①-⑤ 冲突时，必须走变更流程
- ⑤ 红线部分视同宪法级：安全与绝对禁令不因架构让路
- ⑦ 默认权限为零：任何未在前五层登记的行为都需要任务规格授权

#### 裁决速查案例

| 场景 | 冲突 | 裁决 | 正确做法 |
|------|------|------|---------|
| 用户说"先不管架构，赶紧上线" | ⑥用户指令 vs ②蓝图约束 | ② > ⑥ | 走变更流程，更新蓝图后再编码 |
| 任务规格要求绕过红线 | ④任务 vs ⑤红线 | ⑤ > ④ | 拒绝执行，STOP-REPORT |
| 需求与宪法条款冲突 | ③需求 vs ①宪法 | ① > ③ | 先修正需求，使其符合宪法 |
| AI 想"顺手"优化未授权模块 | ⑦AI裁量 vs ④任务范围 | ④ > ⑦ | 不动代码，记入 backlog |
| 架构变更能提升性能但违反不变量 | ②蓝图 vs 不变量 | 不变量 > ② | 保持架构不变，另寻优化方案 |

**记忆口诀**：**安全 > 宪法 > 架构 > 需求 > 任务 > 用户指令 > AI 想法**

#### 2.2.3 通用条款模板

| 条款 | 名称 | 描述 | 判定标准 |
|------|------|------|---------|
| C1 | 原生优先 | 写代码前先检索是否有现成能力 | 新类名与已有功能重叠 → 违例 |
| C2 | 核心质量至上 | 任何变更不得降低核心质量属性 | diff 中出现降级行为 → 违例 |
| C3 | 单一事实源（SSOT） | 一个概念只能有一个实现 | 新增文件与既有文件职责重叠 → 违例 |
| C4 | 最小变更 | 只修改任务规格明确列出的文件 | diff 中出现清单外文件 → 违例 |
| C5 | 先读后写 | 修改前必须先完整读取文件 | 编辑无前置读取记录 → 违例 |
| C6 | 规格先行 | 没有任务规格就不编码 | diff 无法关联任务 ID → 违例 |
| C7 | 配置数据流 | 所有参数走唯一配置链路 | 代码中出现硬编码参数 → 违例 |
| C8 | 学术/引用留痕 | 每个非显然决策有引用注释 | 新引入技术无引用 → 违例 |
| C9 | 诚实汇报 | 汇报中显式区分三态 | 汇报"完成"但无验证证据 → 违例 |
| C10 | 验证义务 | 每次变更后门禁全部执行 | 门禁未全过即标记完成 → 违例 |
| C11 | 停止权 | 含糊/矛盾/超权限时 STOP-REPORT | 以上情形继续编码 → 违例 |
| C12 | 修正案协议 | 宪法自身只能通过修正案变更 | 未经流程直接修改宪法 → 违例 |

#### 2.2.4 宪法模板（可复用）

> **🔧 替换指引**：以下模板中 `[方括号]` 内的内容需要替换为你项目的具体信息。
> 模板是通用的，不依赖任何特定技术栈或项目类型。

```markdown
# 00 — AI 行为宪法

## 第 0 条：项目使命
[对什么用户/场景]，[提供什么能力]，以[核心指标]为首要度量。
# 示例：对移动端用户，提供高并发购物车管理能力，以数据一致性和可用性为首要度量。

## 第一章：为什么需要宪法
[简述项目背景和已出现的跑偏问题]
# 示例：本项目在 AI 辅助开发中出现了双轨冗余、任务粒度失控等问题...

## 第二章：裁决序
① 宪法 > ② 蓝图 > ③ 需求 > ④ 任务 > ⑤ 护栏 > ⑥ 用户指令 > ⑦ AI 裁量

## 第三章：条款
### C1 — [技术栈]原生优先
[描述：写代码前先检索 XXX 框架/库是否有现成能力]。
判定：新类名与已有功能重叠 → 违例
# 示例：C1 — Spring Boot 原生优先。写代码前先检索 Spring Boot 3.x 是否有等价能力。

### C2 — [核心质量]至上
[描述：任何变更不得降低 XXX 属性]。
判定：diff 中出现降级行为 → 违例
# 示例：C2 — 数据一致性至上。任何变更不得降低事务一致性级别。

### C3 — 单一事实源（SSOT）
一个概念只能有一个实现。

### C4 — 最小变更
只修改任务规格明确列出的文件。

### C5 — 先读后写
修改前必须先完整读取文件。

### C6 — 规格先行
没有任务规格就不编码。

### C7 — 配置数据流
所有参数走唯一配置链路。

### C8 — 引用留痕
每个非显然决策有引用注释。

### C9 — 诚实汇报
汇报中显式区分：已完成并验证 / 已完成未验证 / 未完成。

### C10 — 验证义务
每次变更后，四步门禁全部执行、全部通过。

### C11 — 停止权
出现以下情形必须 STOP-REPORT：
1. 规格含糊或矛盾
2. 需要修改未授权文件
3. 无法判断对使命的影响

### C12 — 修正案协议
宪法自身只能通过修正案变更。

## 第四章：违宪症状速查
[症状 → 违反条款的映射表]

## 第五章：制宪配套
[配套文档清单]
```

### 2.3 L1：蓝图（Architecture）

#### 2.3.1 定义

蓝图定义系统的目标架构、模块边界、数据契约与架构不变量。它回答：
- 系统由哪些模块组成？（分层）
- 模块之间如何交互？（依赖矩阵）
- 数据如何在模块间流动？（数据契约）
- 哪些约束是不可违反的？（架构不变量）

#### 2.3.2 分层与依赖规则

**通用分层结构**：

| 层 | 职责 | 规则 |
|----|------|------|
| 编排层 | 入口 + 流程编排 | 不得包含业务逻辑 |
| 核心层 | 配置解析 + 上下文 | 禁止带 `__main__` |
| 阶段层 | 各功能阶段实现 | 彼此只通过上下文交接 |
| 工具层 | CLI 开发/运维工具 | 所有 `__main__` 必须放在此 |
| 支撑层 | 终端展示、日志 | 单向依赖核心层 |
| 数据层 | 声明式资产 | 只读，不包含代码 |

**硬规则**：
1. 阶段层模块之间**只准通过上下文字段交接数据**，禁止直接 import
2. 上下文文件是唯一被全员依赖的枢纽
3. 循环导入的合法解法只有：函数内延迟导入 / TYPE_CHECKING / 合并

#### 2.3.3 数据契约模板

```markdown
## PipelineContext 字段契约

| 字段 | 唯一写者 | 读者 | 类型 | 约束 |
|------|---------|------|------|------|
| `field_a` | 阶段 X | 阶段 Y, Z | dict | not_empty |
| `field_b` | 阶段 Y | 阶段 Z | list | len > 0 |

## 数据传递规则

| 规则 | 说明 |
|------|------|
| X→Y | `field_a` 非空 + `field_b` 非空 |
| Y→Z | `field_b` 包含所有必要数据 |
```

| # | 不变量 | 依据 | 检查方式 |
|---|--------|------|---------|
| I1 | [约束描述] | [学术引用/设计决策] | guard / dry-run |
| I2 | [约束描述] | [学术引用/设计决策] | guard / dry-run |

```markdown
## 架构债务登记簿（冻结区）

| ID | 债务 | 现状 | 消除方向 |
|----|------|------|---------|
```

### 2.4 L2：需求（Requirements）

#### 2.4.1 定义

需求是所有"做什么"的唯一登记处。**未登记的需求 = 不存在**。

#### 2.4.2 需求分级

| 级别 | 定义 | 变更门槛 |
|------|------|---------|
| P0 | 主链路：系统核心功能 | 修改需 change-proposal + 评审 |
| P1 | 支撑能力：配置、可观测性 | 修改需规格变更 |
| P2 | 体验与优化：UI、性能 | 可经普通任务变更 |

#### 2.4.3 需求格式

```markdown
## P0 — 主链路需求

| ID | 陈述 | 验收标准 | 状态 |
|----|------|---------|------|
| REQ-001 | [一句话需求] | ① [可勾选] ② [可勾选] | ✅ / ⚡ / ❌ |
```

#### 2.4.4 负需求（禁止清单）

```markdown
## 负需求

| ID | 禁止事项 | 理由 |
|----|---------|------|
| NEG-1 | 禁止扩展双轨/债务 | SSOT |
| NEG-2 | 禁止在核心链路添加降级逻辑 | 核心质量至上 |
| NEG-3 | 禁止绕过数据契约新开通道 | 架构约束 |
| NEG-4 | 禁止引入新运行时依赖（提案制） | 供应链安全 |
```

#### 2.4.5 需求变更流程

```
想法 → change-proposal 填写件
     → 人工评审（批准/驳回/转 backlog）
     → 批准：登记 REQ/DEBT 条目（含验收标准）
     → 生成任务规格
     → 编码
```

### 2.5 L3：任务（Tasks）

#### 2.5.1 定义

任务定义"怎么做"——将需求分解为可执行的原子操作。

#### 2.5.2 粒度上限

| 维度 | 上限 | 超限处理 |
|------|------|---------|
| 文件数 | ≤3 | 先拆分 |
| diff 行数 | ≤300 | 先拆分 |
| 跨模块数 | ≤2 | 先拆分 |
| 新增文件 | ≤1 | 先拆分 |

#### 2.5.3 开发三元组（防跑偏核心机制）

> **核心理念**：将开发全生命周期拆为三个不可绕过的检查点，每个点有明确输入/输出。

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                        开发三元组（开发全审）                                 │
│                                                                             │
│   ┌──────────────┐      ┌──────────────┐      ┌──────────────┐             │
│   │  开发前      │      │  开发中      │      │  开发后      │             │
│   │  ─────────   │      │  ─────────   │      │  ─────────   │             │
```

##### 阶段 1：开发必看（开发规范）—— 开发前不可绕过

**输入**：任务目标、涉及的模块  
**动作**：阅读相关规约文档  
**输出**：理解规则、明确边界

| 必看内容 | 文档位置 | 必须回答的问题 |
|---------|---------|---------------|
| 宪法 | 00-CONSTITUTION.md | 这个项目最不能违反的规则是什么？ |
| 蓝图 | 10-ARCHITECTURE.md | 我要改的模块在哪个层级？依赖谁？ |
| 需求 | 20-REQUIREMENTS.md | 这个任务的验收标准是什么？ |
| 红线 | 40-GUARDRAILS.md | 哪些代码模式是绝对禁止的？ |
| 债务 | backlog.md | 有没有相关的已知债务和冻结区？ |

##### 阶段 2：开发必跑（开发验证）—— 开发中不可绕过

**输入**：改完的代码  
**动作**：按顺序执行 6 步检查，每步通过才进下一步  
**输出**：所有检查 PASS 的记录

> **🔧 替换指引**：以下命令是通用示例，请替换为你项目的实际命令。
> - `[GUARD_CMD]` → 你的架构规则检查命令
> - `[LINT_CMD]` → 你的代码风格检查命令
> - `[TEST_CMD]` → 你的单元测试命令
> - `[DRYRUN_CMD]` → 你的运行时验证命令
> - `[DRIFT_CMD]` → 你的规范漂移检测命令
> - `[DATAFLOW_CMD]` → 你的数据流完整性测试命令

| 步 | 命令（通用占位符） | 命令（示例） | 通过标准 | 失败处理 |
|----|-------------------|-------------|---------|---------|
| 1 | `[GUARD_CMD]` | `py -m tools.guard` | 0 新增 BLOCKING | 修复红线违例 |
| 2 | `[LINT_CMD]` | `ruff check . --fix` | 0 违规 | 自动修复后重跑 |
| 3 | `[TEST_CMD]` | `pytest tests/ -v --tb=short` | 0 失败 | 分析失败原因，修复后重跑 |
| 4 | `[DRYRUN_CMD]` | `python main.py --dry-run` | 无 ImportError/AttributeError | 修复数据流断点 |
| 5 | `[DRIFT_CMD]` | `py -m tools.drift_detector --full` | 0 BLOCKING | 修复规范漂移 |
| 6 | `[DATAFLOW_CMD]` | `pytest tests/test_data_flow_integrity.py` | 0 失败 | 修复数据契约违例 |

**不同技术栈的命令示例**：

| 技术栈 | `[LINT_CMD]` | `[TEST_CMD]` | `[DRYRUN_CMD]` |
|--------|-------------|-------------|----------------|
| Python | `ruff check . --fix` | `pytest tests/ -v` | `python main.py --dry-run` |
| JavaScript/TypeScript | `eslint . --fix` | `jest --passWithNoTests` | `npm run build` |
| Go | `golangci-lint run` | `go test ./...` | `go build ./...` |
| Java | `mvn checkstyle:check` | `mvn test` | `mvn compile` |

### 2.6 L4：护栏（Guardrails）

#### 2.6.1 定义

护栏定义"别越线"——红线是绝对禁止，门禁是完成任务的必要条件。

#### 2.6.2 红线分类

| 类别 | 级别 | 检查方式 | 后果 |
|------|------|---------|------|
| 机器红线（R-L） | BLOCKING | guard 自动检查 | 阻断 commit/push |
| 人工红线（R-H） | WARNING | diff 评审 | 评审驳回 |
| 安全红线（R-S） | BLOCKING | 人工评审 | 最严重违例 |

#### 2.6.3 通用红线清单

| # | 红线 | 检查器 |
|---|------|--------|
| R-L1 | [业务逻辑红线] | `check_red_line_1()` |
| R-L2 | 自定义基类替代框架原生 | `check_native_first()` |
| R-L3 | [技术栈约束违规] | `check_tech_stack()` |
| R-H1 | 静默降级：stub/空实现进入主干 | `check_stub()` |
| R-H2 | 静默吞错：`except: pass` | `check_bare_except()` |
| R-H3 | 双轨新增：职责重叠 | `check_dual_track()` |
| R-H4 | 配置断点：硬编码参数 | `check_hardcoded()` |
| R-H5 | 数据旁路：绕过契约新开通道 | `check_data_bypass()` |
| R-H6 | 规格蒸发：diff 无法关联需求 | `check_spec_link()` |
| R-H7 | 证据注水：汇报未实际验证 | `check_verification()` |

#### 2.6.4 四步门禁

| 步 | 命令 | 通过标准 | 拦截什么 |
|----|------|---------|---------|
| 1 | 静态检查（guard） | 0 新增 BLOCKING | 架构模式违规 |
| 2 | 代码风格（lint） | 0 违规 | 风格/导入/未用变量 |
| 3 | 单元测试 | 0 失败 | 功能回归 |
| 4 | 运行时验证（dry-run） | 无 ImportError/AttributeError | 数据流断点 |

#### 2.6.5 三层防线

| 层 | 机制 | 运行时机 |
|----|------|---------|
| L1 静态 | guard 检查 | pre-commit / 手动 |
| L2 运行时 | dry-run / 测试 | 每次变更后 |
| L3 Git 门禁 | hooks 阻断 | commit / push |

| 3 | **"顺手"扩范围** | C4 最小 diff + 评审清单 | 改动面失控 → 评审无法判定 |

### 3.6 STOP-REPORT 熔断机制

> **来源**：30-TASKS 第五章（偏航熔断）。执行中出现以下任一信号，必须立即停止编码。

#### 触发信号

1. 需要修改 task-spec 之外的文件（含"只是顺手"）
2. 发现规格与代码现实不符（要改的东西不存在/已被改掉/结构不同）
3. 发现需要新增依赖/新文件/new ctx 字段/new 配置参数而规格未授权
4. 预计超出粒度上限（文件>3 / diff>300 / 模块>2）
5. 发现实现路径会触碰红线
6. 对"这个变更让核心指标升还是降"无法给出有据答案

#### STOP-REPORT 格式（一次性输出）

```markdown
## STOP-REPORT
- 触发条款: C4/C11（哪一条）
- 现状: （一句话：我正在做什么、发现了什么）
- 矛盾: 规格说 X / 代码现实是 Y / 红线 Z
- 选项:
  A. 修改任务规格，纳入新范围（估计 +N 文件/+M 行）
  B. 缩小当前任务，新发现登记 backlog
  C. 中止任务（原因）
- 我的建议: B（一句话理由）
```

**绝对禁止**：把 STOP-REPORT 的三个选项合并成"我都做了"。猜着做 = 违宪；停下来问 = 合宪。

### 3.7 任务生命周期完整流转

> **来源**：30-TASKS 第一章。一个任务从生到死的完整状态机。

```
draft（草案） → spec'd（规格完成） → approved（人工批准）
     → in-progress（执行中） → verified（四步门禁通过）
     → closed（关闭） / aborted（中止，须记录原因）
```

| 状态转换 | 必要动作 | 禁止行为 |
|---------|---------|---------|
| draft → spec'd | 填写 task-spec 全部字段，无空项 | 跳过字段 |
| spec'd → approved | 人工评审签字 | 未经批准直接编码 |
| in-progress 变更范围 | STOP-REPORT | 静默扩权 |
| verified | C10 四步门禁全部通过 + 验收标准逐条勾选 | 门禁未过即标完成 |
| aborted | backlog 留一行记录（做了什么/为何停/留下状态） | 无声消失 |

**判断原子性的标准**：如果一个任务的 diff 需要两个不同的 commit message 来描述，它就是两个任务。

### 3.8 禁止行为清单

> **来源**：30-TASKS 第七章。每次执行时的硬禁令。

| # | 禁止行为 | 理由 | 违反后果 |
|---|---------|------|---------|
| 1 | 编码前不复述计划 | Step 5 闸门失效 | 直接驳回 |
| 2 | 修改未读取的文件 | C5 违宪 | 修正任务 |
| 3 | 一个 diff 混合功能+重构+格式化 | C4；评审无法判定语义 | 拆分 diff |
| 4 | 静默吞异常（`except: pass` 无日志无说明） | C9；吞错 = 隐瞒 | 重写异常处理 |
| 5 | 留 `TODO/FIXME/XXX` 进主干而不登记 backlog | 债务暗增 | 补登 backlog |
| 6 | 删除报错的测试来"让 pytest 通过" | 证据造假 | 修正测试或 STOP |
| 7 | 为通过 guard 而改 guard | 规则破坏 | 修正代码而非检查器 |
| 8 | 提交含密钥/真实端点的文件 | 安全红线 | 立即 revert |
| 9 | 汇报中省略"未验证"栏 | C9 违宪 | 补全汇报 |
| 10 | 顺手修债务（未持专项任务规格） | 范围失控 | 登记 backlog，不动代码 |

### 3.9 变更前基线与回滚协议

> **来源**：40-GUARDRAILS 第四章。任务开始时的标准动作。

#### 基线记录（任务开始时）

```bash
# 记录当前违规基线
py -m tools.guard > outputs/guard_baseline.json
```

**通过标准是"不新增"**：存量违规（历史 WARNING）允许存在，但 BLOCKING 存量必须登记为 DEBT/backlog，禁止视而不见。

#### 回滚协议

| 情形 | 动作 | 后续 |
|------|------|------|
| 门禁失败且 10 分钟内无法定位 | `git checkout -- <files>` 回滚全部变更 | 任务转 aborted，记录根因 |
| Tier 2 运行时验证异常 | 保留代码 + 任务停在 verified-前 | 汇报 ⚠️ 栏说明，不标 completed |
| 合入后发现回归 | revert 该 commit（不修新补丁覆盖） | 重新走任务流程 |

**禁止**：在未回滚的情况下叠加"修复修复"的二次 diff。

### 3.10 自主决策护栏

> **来源**：40-GUARDRAILS 第五章。当 AI 需要自主判断时，以下护栏确保决策不失控。

#### 护栏决策表

| 情形 | 决策权 | 需要报告 |
|------|--------|---------|
| 参数选择（默认值/配置） | AI 自主 | 无需 |
| 模式选择（同步/异步） | AI 自主 | 无需 |
| 文件结构（函数拆分方式） | AI 自主 | 无需 |
| 新增文件 | 需人工批准 | 是 |
| 新增依赖 | 需人工批准 | 是 |
| 修改 ≥3 个文件 | 需人工批准 | 是 |
| 触达红线边界 | STOP-REPORT | 是 |
| 超出任务规格范围 | STOP-REPORT | 是 |

#### 护栏分级触发

```
AI 判断开始
    │
    ├── 决策涉及红线/安全？
    │       └── 是 → STOP-REPORT，等待人工决策
    │
    ├── 决策涉及新增文件/依赖？
    │       └── 是 → 提出建议，等人工确认
    │
    ├── 决策涉及 ≥3 文件修改？
    │       └── 是 → 缩小范围或请求批准
    │
    └── 决策在授权范围内？
            └── 是 → 自主执行，记录到 orchestration_log
```

**纪律**：AI 在授权边界内自主决策时，必须记录决策理由；超出边界时必须 STOP-REPORT，不得自行扩权。

## 第七部分：FAQ

### Q1：规范越多越好吗？

**A**：不是。规范应该**刚好够用**。

- 3 条规则能解决 → 不要写 13 条
- lint 够用 → 不需要 34 个检查器
- 规范是**约束行为边界**，不是**束缚创造力**

### Q2：AI 不遵守宪法怎么办？

**A**：纯文本约束容易被忽略，需要配套自动化检查器。

- 每条红线对应一个 guard 检查器
- 检查器安装为 git hook
- BLOCKING 级别自动阻断

### Q3：规范会拖慢开发速度吗？

**A**：会牺牲一点"绝对速度"，但避免了大量"跑偏修复"时间。

| 阶段 | 无规范 | 有规范 |
|------|--------|--------|
| 初始开发 | 快 | 稍慢（需写规格） |
| 中期维护 | 慢（双轨/回归） | 快（清晰有序） |
| 长期演进 | 很慢（技术债务） | 快（债务可见可控） |

### Q4：规范和敏捷冲突吗？

**A**：不冲突。规范是交通规则，敏捷是目的地。

- 交通规则让你不翻车
- 目的地让你知道去哪
- 开车方式由你决定

### Q5：如何让 AI"记住"宪法？

**A**：三种方式结合：

1. **文件存在**：宪法文件在项目中，AI 可以读取
2. **工具集成**：guard 检查器自动执行红线
3. **触发词**：如"完整验证"自动触发全量检查

### Q6：规范需要定期更新吗？

**A**：需要。规范应该随项目成长而演进。

- 宪法：走修正案流程
- 蓝图：走变更流程
- 护栏：按需调整检查器
- 频率：建议每月回顾一次

### Q7：AI 产出了看起来正确但实际错误的代码怎么办？

**A**：这是最常见的风险。处理方式：

1. **不要信任 AI 的"看起来对"**：每个 API 调用都要验证
2. **测试是最好的过滤器**：AI 幻觉通常会在测试中暴露
3. **使用类型检查**：mypy/pyright 可以捕获类型错误
4. **记录已知幻觉**：在 backlog 中记录 AI 常犯的错误类型

### Q8：如何判断一个任务是否需要完整八步协议？

**A**：使用以下决策树：

```
任务开始
    │
    ├── 改动 ≤50 行 且 不涉及核心模块？
    │       └── 是 → 简化流程（Step 4-5-7 即可）
    │
    ├── 涉及核心模块 或 改动 >200 行？
    │       └── 是 → 完整八步协议
    │
    └── 涉及新模块/新文件？
            └── 是 → 完整八步协议 + 架构评审
```

### 附录 C：常见排错速查

| 症状 | 可能原因 | 解决方案 |
|------|---------|---------|
| `ModuleNotFoundError` | 依赖未安装 / 虚拟环境未激活 | `pip install -r requirements.txt` |
| `ImportError` 循环导入 | 架构层级违反 | 改为函数内延迟导入 |
| 测试全部通过但功能错 | 测试覆盖不足 / 测试本身有 bug | 检查断言是否正确 |
| guard 报 BLOCKING | 红线被违反 | 运行 `py -m tools.guard -v` 查看详情 |
| AI 产出不存在 API | AI 幻觉 | 手动验证 API 是否存在 |
| lint 报大量错误 | 未配置 ruff / 代码风格不一致 | `ruff check . --fix` |
| dry-run 通过但实际运行失败 | 测试环境与生产环境不一致 | 检查配置、依赖版本 |

### 附录 D：术语表

| 术语 | 定义 |
|------|------|
| **ASR** | Attack Success Rate，攻击成功率 = 成功攻击数 / 总攻击数 |
| **SSOT** | Single Source of Truth，单一事实源——一个概念只能有一个实现 |
| **BLOCKING** |  guard 检查级别，违例会阻断 commit/push |
| **WARNING** | guard 检查级别，违例会警告但不阻断 |
| **INFO** | guard 检查级别，仅提示信息 |
| **dry-run** | 运行时验证模式，不实际执行攻击，只验证数据流 |
| **门禁** | 四步质量检查：guard → lint → test → dry-run |
| **backlog** | 唯一待办池，记录发现的非本任务问题 |
| **ctx** | PipelineContext，流水线上下文——阶段间数据交换的唯一枢纽 |
| **不变量** | 任何变更不得破坏的硬性架构约束 |
| **债务** | 已识别的架构/代码问题，登记后冻结，专项消除 |
| **PoC** | Proof of Concept，可独立运行的概念验证脚本 |
| **Vibe Coding** | 氛围编码——让 AI 自由发挥的编程方式，风险是跑偏 |
| **Glue 代码** | 连接现有原生组件的胶水层——自研代码的合法角色之一 |
| **Enhancement 代码** | 在现有原生组件基础上增强功能——自研代码的合法角色之一 |
| **Output 代码** | 结果输出/展示层——自研代码的合法角色之一 |
| **FIRST_SUCCESS** | 短路策略——首条路径成功后立即停止当前种子其他路径 |
| **0-token 评分** | 不使用 LLM token 的评分器（如规则匹配、关键词检测） |
| **OR 聚合** | 多个评分器结果取 OR（任一成功即成功）——ASR 最大化策略 |

### 附录 E：版本控制策略

**分支模型**：

```
main (生产分支，始终可部署)
  │
  ├── feature/TASK-xxx (功能分支，从 main 分出)
  │     └── 开发 → 门禁 → PR → review → merge
  │
  ├── fix/TASK-xxx (修复分支)
  │     └── 开发 → 门禁 → PR → review → merge
  │
  └── debt/DEBT-xxx (债务消除分支)
        └── 开发 → 门禁 → PR → review → merge
```

**提交信息规范**：

```
<type>(<scope>): <TASK-xxx> <描述>

type:
  feat: 新增功能
  fix: 修复 bug
  refactor: 重构
  test: 测试
  docs: 文档
  debt: 债务消除

示例:
  feat(strike): TASK-042 新增供应链攻击模块
  fix(assess): TASK-043 修复 Wilson CI 计算精度问题
```

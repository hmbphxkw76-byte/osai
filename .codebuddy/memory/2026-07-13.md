### PyRITMultiTurnOrchestrator 核心能力
- **Crescendo 攻击**: 5轮逐步升级，从无害问题渐变到恶意请求
  - PyRIT 原生 `CrescendoOrchestrator`（自动对话编排 + 攻击者LLM + 评分）
  - 本地 fallback：5种递增载荷链（探索→技术讨论→试探→升级→攻击）
- **TAP 攻击**: Tree of Attacks with Pruning（分支攻击树 + 剪枝优化）
  - 支持 branching_factor（分支数）和 max_depth（深度）配置
  - 5种初始分支模板（直接注入/角色扮演/学术伪装/翻译绕过/编码绕过）
  - 5种变异策略（前缀强化/上下文追加/编码重组/压力型/多语言混合）
- **PAIR 攻击**: Prompt Automatic Iterative Refinement（迭代优化）
  - 基于响应反馈的智能攻击提示优化
  - 拒绝→切换策略，低分→增加合法性，中分→强化目标，高分→冲刺
- **RedTeamingOrchestrator**: 全自动红队编排（PyRIT 原生）

### PyRITScoringOrchestrator 核心能力

- 自动回退到本地 HybridScorer
- True/False 评分 + 分类评分

## 无 LLM 考试模式 — 评分器全链路离线化

### 问题诊断
用户指出 OffSec AI-300 考试期间可能不允许使用外部 LLM 模型，当前评分体系有 3 个致命问题：

1. **`PyRITAttackRunner.run()` 失败时返回全 0 分** (`runner.py:358,368,392`)
   - PyRIT 执行失败 → `_fallback_results()` → score=0.0, success=False
   - 攻击即使成功，评分也归零，所有 Finding 丢失
2. **`ScenarioOrchestrator._build_runner()` 默认 `["true_false"]`** (`orchestrator.py:124`)
   - `true_false` → `SelfAskTrueFalseScorer` 需要 judge LLM endpoint
   - 考试环境无 judge endpoint → PyRIT 失败 → 全零评分
3. **`prompt_inject.py` 3 处硬编码 `scorers=["true_false"]`** (line 359,404,437)
   - 同样问题：依赖 LLM Judge

根本原因：`PyRITAttackRunner` 把评分完全委托给 PyRIT，PyRIT 失败后直接返回全零，
本地的 `HybridScorer`/`FastGrayscaleScorer` 被完全绕过。

### 修复方案

#### Fix 1: `PyRITAttackRunner` — 添加 `_native_fallback()` 方法
- 新增 `_fallback_scorer`（HybridScorer/FastGrayscaleScorer）
- 新增 `_force_local_scoring` 标志（响应 `REDTEAM_NO_JUDGE_LLM=1`）
- 新增 `_native_fallback()` 方法：真实发送 HTTP 请求 + 本地多维度评分
- 替代原有 `_fallback_results()`（不再返回全 0 结果）
- PyRIT 执行失败 → 自动降级到本地 httpx + HybridScorer 评分

#### Fix 2: `ScenarioOrchestrator._build_runner()` — 默认本地评分
- 检查 `REDTEAM_JUDGE_ENDPOINT` 环境变量
- 已设置 → `scorers=["true_false"]`（LLM-as-Judge）
- 未设置（默认/考试）→ `scorers=["hybrid"]`（本地规则评分）

#### Fix 3: `prompt_inject.py` + `agent_attack.py` — 动态评分器选择
- 新增 `default_scorers()` 函数（`runner.py`）
  - `REDTEAM_JUDGE_ENDPOINT` 已设置 → `["true_false"]`
  - `REDTEAM_NO_JUDGE_LLM=1` → `["hybrid"]`（强制本地）
  - 默认 → `["hybrid"]`
- 替换所有硬编码 `scorers=["true_false"]` → `scorers=default_scorers()`
- 导出到 `core/__init__.py`、`pyrit_runner.py`

#### 新增环境变量
| 变量 | 作用 |
|------|------|
| `REDTEAM_NO_JUDGE_LLM=1` | 强制使用本地评分器，不使用任何 LLM Judge |
| `REDTEAM_JUDGE_ENDPOINT` | 指定 Judge LLM 端点（非考试环境可选） |

## LLM-as-Judge 评分器全链路打通 + CLI 命令更新

### 问题修复
上次修复确保「无 LLM 时评分正常工作」，但反向路径（有 LLM Judge 时）有 3 个 bug：

1. **`PyRITAttackRunner._build_attack()` 把攻击目标 URL 当 Judge 端点** (line 352)
   - `_build_scorers(self.scorer_names, self.target_url)` → SelfAskTrueFalseScorer 指向目标自身
   - 目标 LLM 评自己的响应 → 越狱后会说 "我没问题" → 评分失真
2. **`ScenarioOrchestrator._build_runner()` 检查了 `REDTEAM_JUDGE_ENDPOINT` 但没传给 runner**
   - 只决定用哪个 scorer 名称，不传实际端点

#### Fix 2: `runner.py` — `PyRITAttackRunner` 增加 `judge_endpoint` 参数

## Scenarios ↔ Payloads 断裂修复 — PayloadBridge 桥接层

### 问题诊断

发现两层断裂：
1. **Scenarios 之间互不引用** — 7个YAML各自独立，agent.yaml不引用generic.yaml
2. **Scenarios 不引用 config/payloads/** — orchestrator.py 无任何 PayloadLoader 导入，全靠内嵌 `{objective}` 占位符

### 修复方案

创建三层桥接机制：

| 层 | 文件 | 功能 |
|----|------|------|
| **桥接模块** | `redteam/scenario/payload_bridge.py` | 连接载荷库与场景 |
| **Schema 扩展** | `redteam/scenario/schema.py` | `model_config = {"extra": "allow"}` |
| **Loader 集成** | `redteam/scenario/loader.py` | 加载时自动通过桥接丰富 |
| **场景配置** | 7个YAML + extends/payload_sources | 声明继承和库引用 |

### PayloadBridge 核心功能

1. **extends 跨场景继承**：
   - `extends: "generic"` → 自动合并基场景的阶段和载荷
   - 去重逻辑：当前场景优先（同名阶段跳过，同ID载荷跳过）

2. **payload_sources 库载荷引用**：
   - `source: library` — 从 config/payloads/ 加载
   - `categories: [llm01, llm02, ...]` — 指定OWASP类别
   - 未指定 strategies → 全量加载模式（自动匹配技术→策略）
   - 指定 strategies → 精准过滤模式

3. **STRATEGY_TO_PAYLOAD_CATEGORIES 映射表**：
   - 30+ AttackStrategy → OWASP类别映射
   - direct_inject → llm01, goal_hijack → llm02 等

4. **LIBRARY_TECHNIQUE_TO_STRATEGY 映射表**：
   - 库载荷 technique → AttackStrategy 精确映射
   - instruction_override → DIRECT_INJECT, roleplay → ROLEPLAY/JAILBREAK 等
   - 未命中时使用关键词宽松匹配 + 场景策略回退

5. **类别级缓存**：避免同一类别重复加载（如 agent.yaml 的 llm01 被加载13次 → 变为1次）

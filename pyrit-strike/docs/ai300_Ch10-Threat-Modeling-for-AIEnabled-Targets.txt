=== Chapter 10: Threat Modeling ===

This course develops the skills needed to conduct offensive operations against AI-enabled enterprise systems. It enables learners to apply structured methodologies when operating in realistic, AI-driven environments. 

### 10. Threat Modeling for AI-Enabled Targets 
Every attack chain in this course, from prompt injection to
multi-agent pivots and supply chain compromise, began with choosing where to attack. That choice was guided by some understanding of the
target, whether deliberate or intuitive. 
In this Learning Module, we'll formalize that instinct into a
repeatable methodology. 
Unlike a textbook decomposition where the full architecture is laid
out in advance, real engagements start with fragments: a scoping
document, a handful of DNS records, some job postings, and a lot of
assumptions. The threat model is not a product we build before the
engagement and then execute. It is a living artifact that evolves with
every piece of intelligence we collect, every assumption we validate
or discard, and every scope constraint that eliminates a theoretical
path. 
We will work through a simulated engagement against Nexus AI ,
an enterprise Artificial Intelligence for IT Operations (AIOps)
platform. We will reconstruct its architecture from partial
information, form and track hypotheses, hit rules of engagement that
force us to abandon promising attack paths, and make time-pressured
decisions with incomplete data. The output is an attack intelligence
brief , the artifact that tells us which target to pursue next based
on what we know right now . 
This Module contains the following Learning Units: 

- Reconstructing the Target from Partial Intelligence : Building an
architectural picture of an AI-enabled target from pre-engagement
artifacts and progressive reconnaissance. Tracking assumptions with
confidence ratings, validate or discard them as new information
arrives, and maintain an evolving component inventory mapped to
MITRE ATLAS technique IDs. 
- Trust Zones, Escalation Paths, and Engagement Planning : Define
trust zone boundaries, trace escalation paths through them, apply
scope and rules of engagement as hard constraints, prioritize paths
under time pressure, and produce an actionable attack intelligence
brief. 

### 10.1. Reconstructing the Target from Partial Intelligence 
This Learning Unit covers the following Learning Objectives: 

- Reconstruct the architecture of an AI-enabled target from incomplete
pre-engagement information 
- Maintain an assumption register that tracks observations,
hypotheses, confidence levels, and validation status 
- Update the threat model iteratively as new intelligence confirms or
invalidates working assumptions 
- Identify and rank crown jewels by their offensive value given
current knowledge 
- Map confirmed components to MITRE ATLAS technique IDs to inform
tradecraft selection In a real engagement, nobody hands us the architecture diagram. We
reconstruct it from scoping documents, public repositories, DNS
records, job postings, cloud metadata, and whatever we can discover
during initial reconnaissance. Every component we identify starts as a
hypothesis with a confidence level. Some hypotheses survive testing.
Others collapse, and the threat model shifts underneath us. 
This Learning Unit walks through that reconstruction process against
our target, Nexus AI. We'll start with what the client gave us and
what we can find publicly, then progressively build the picture as we
collect intelligence during the engagement. 

Our engagement against Nexus AI begins with three artifacts: a scoping
document from the client, the results of passive Open Source
Intelligence (OSINT) collection, and some minimal pre-engagement
technical documentation the client shared during kickoff. This is a
dedicated AI security assessment under the broader Megacorp One
program — the client has specifically carved out the Nexus AI platform
as an in-scope target for grey-box testing.

OSINT Collection (passive): 

- A LinkedIn search for "Nexus AI" at Megacorp Financial Services
surfaces several job postings and employee profiles. 
- One posting for a "Senior ML Platform Engineer" mentions experience

- A DevOps engineer's profile lists "HashiCorp Vault" and "MCP

- A recently-closed GitHub issue on a public fork of an MCP server

During kickoff, the client shared a high-level data flow description:
"Alerts from monitoring systems flow into a central orchestrator,
which routes them to specialized agents for triage, remediation, and
security analysis. Agents consult a shared knowledge base for context
and execute actions through a central tool server". 
This is everything we have so far: We have no architecture diagram, no
port list, and no component inventory. From this point, we'll build
out our model and try to get it to match reality as much as we can. 

Before we can begin active reconnaissance, let's formalize what we
think we know. An assumption register tracks every hypothesis about
the target, its source, our confidence in it, and its current
validation status. This is the backbone of iterative threat modeling,
which prevents us from treating guesses as facts and ensures we know
exactly what needs verification.

Every hypothesis follows this lifecycle, from initial observation
through validation testing to either VALIDATED (drives attack
planning) or INVALIDATED (generates new hypotheses). The feedback loop
is what makes iterative threat modeling work.

Info 

Notice that A-07 has LOW confidence and is flagged as "absence
of evidence". The client documentation does not mention vector
database authentication — but that does not mean authentication is
absent. It means we have not seen evidence either way. This
distinction matters. LOW confidence assumptions drive verification
tasks early in the engagement; they do not drive attack planning
until more confidence is warranted from additional evidence. Treating
the absence of information as confirmation of a vulnerability is one
of the most common mistakes in pre-engagement threat modeling. 

The assumption register is a living document. Every time we collect
new intelligence - a port scan result, an API response, a
configuration file - we update it: promoting hypotheses to VALIDATED,
demoting them to INVALIDATED, adjusting confidence levels, and adding
new entries. Our threat model is only as good as the assumptions it
rests on.

Before we start pulling data, we need to check the scoping document:

Info 

This is the
moment where theoretical threat modeling and real engagement planning
diverge. In an unconstrained analysis, poisoning the production vector
database is the most efficient escalation path — it requires no
authentication and influences every downstream agent. However, the RoE
prohibits this. A common mistake is to include RoE-prohibited paths in
the attack plan with a note saying "if the client approves". That is
not how most engagements work. The RoE is a hard constraint. Let's
remove the path from our active plan and redirect our efforts. The
path still belongs in the final report as a risk finding (the
database is unauthenticated), but it does not belong in our engagement
execution plan.

A-12b is critical. We know the Remediation Agent token works for vault_rotate_secret , but we have not confirmed that the same token
authorizes aws_cli_exec . The JWT scope claims we extracted suggest
per-tool scoping, but we deliberately avoided testing aws_cli_exec during Phase 2 to limit our detection footprint. If the Remediation
Agent token does not authorize aws_cli_exec , Path 1 requires a
different token — potentially one we do not hold yet. 
A-12c matters for attribution. If Vault cannot distinguish which agent
triggered a request, then any MCP tool invocation using any valid
agent token will appear identical in Vault's audit log. This means our
use of the Remediation Agent's stolen token will not stand out at the
Vault layer — but it may still be detectable at the MCP Server layer
if the MCP Server logs which token was used.

production. Inverting the staging instance (i.e. reading its contents
rather than writing to them) may yield topology information,
credential patterns, or deployment procedures that inform our attack
planning. The RoE permits reads from staging, and it is
unauthenticated like its production counterpart.

At this point, we have completed three phases of intelligence
collection and our threat model has evolved significantly from the
pre-engagement starting point. Let's take stock of where the model
stands. 
What we know (VALIDATED): Four agents, one orchestrator, one MCP
server with per-agent tool authorization, Qdrant unauthenticated,
Vault unsealed, MLflow present. The Remediation Agent can rotate Vault
secrets via vault_rotate_secret — and we hold this token (extracted
from Kubernetes secrets). Five detection rules have been extracted.
Agent-to-agent bypass is monitored. MCP calls are monitored by tool
name and timing, but potentially not by parameter content. 
What we don't know (UNVALIDATED): Whether the Remediation Agent
token also authorizes aws_cli_exec (A-12b — critical for Path 1).
Whether agent identity collapses at the Vault boundary (A-12c). How
the Orchestrator dispatches tasks (A-01 says it routes, but we have
not confirmed the dispatch mechanism). Whether webhook ingestion
requires authentication (affects alert manipulation paths). Whether
MLflow requires authentication for model reads or writes. Whether
additional detection mechanisms exist outside the Qdrant-stored rules. 
What is blocked (RoE constraints): Production vector database
poisoning. Denial-of-service testing. Any actions against production
financial systems or AD domain controllers. MCP tool invocations must
be reported within 24 hours. This means any MCP-based attack path has
a 24-hour detection window built in — the Blue Team will know what
tools we used, even if automated detection does not trigger. 
What has changed since Phase 1: The most significant shift is that
the flat credential model we hypothesized (A-08 original) turned out
to be partially wrong : the MCP Server does enforce per-agent tool
scoping. This is good news for the defender (not every agent can do
everything

=== Chapter 3: Attacking AI Agents ===

This course develops the skills needed to conduct offensive operations against AI-enabled enterprise systems. It enables learners to apply structured methodologies when operating in realistic, AI-driven environments. 

### 3. Attacking AI Agents 
This Learning Module covers the following Learning Units: 

- Understanding Single-Agent Architecture 
- Direct Prompt Injection 
- Indirect Prompt Injection 
- Agent Memory Attacks Enterprises are deploying AI agents to automate workflows, from IT
helpdesks and document processors to code review assistants and knowledge
base managers. Unlike simple chatbots that generate text, agents can reason
through multi-step tasks, call tools, access internal systems, and maintain
memory across sessions. That autonomy is what makes them powerful, and also
what makes them vulnerable. 
In this Module, we'll attack AI agents the way a red teamer would on an
engagement. We'll enumerate agent services, extract their internal
configurations, hijack their objectives, poison their data sources, and
persist across sessions. Every attack follows the same cycle: enumerate the
target, execute a naive attack, observe the detection, then evade it. By the
end, you'll have a repeatable methodology for testing any AI agent deployment
you encounter in the field. 

### 3.1. Understanding Single-agent Architecture 
In this Learning Unit, we'll cover the following Learning Objectives: 

- Understand the components that make up an AI agent 
- Identify the attack surface of a deployed AI agent 
- Apply the enumerate-attack-detect-evade cycle used throughout this Module Before we start injecting payloads and stealing credentials, we need to
understand what we're attacking. AI agents aren't black boxes. They're
built from distinct components, each with its own attack surface. In this
Learning Unit, we'll break down how agents work, map out where we can
intervene, and introduce the methodology we'll use for every attack in the
Module. 

A chatbot takes your message, passes it to a language model, and
returns the response. That's a single round trip. An agent does
something fundamentally different. It receives your message, reasons about what to do, decides which tools to call, executes those
tools, observes the results, and then either takes another action or
responds. It can do this for multiple steps, chaining actions together
to complete complex tasks. 
This distinction matters for red teamers because agents have a much
larger attack surface than chatbots. A chatbot can only leak text. An
agent can read files, query databases, fetch web pages, write to
storage, and call APIs, all based on what it's told to do. If we can
control what it's told, we control what it does. 
Enterprises are deploying agents for real workflows: IT helpdesks that
diagnose issues and look up configurations, document processors that
summarize and route files, code review assistants that read your
codebase, and product lookup agents with access to internal pricing
data. Each of these has legitimate access to internal systems, and
that access becomes our attack surface. 

Every agent in our lab, and most agents you'll encounter in the field,
is built from five core components. 
The LLM core is the reasoning engine. It processes everything as
tokens: system prompts, user input, tool outputs, and memory. It
doesn't distinguish between these sources. They all arrive in the same
token stream, and this lack of trust boundaries is the foundation of
every attack in this Module. 
The system prompt is a set of hidden instructions that define the
agent's identity, rules, restrictions, available tools, and behavioral
boundaries. System prompts often contain sensitive information:
internal URLs, database credentials, API keys, filter keyword lists,
and security rules. They're hidden from the user but visible to the
LLM, and as we'll see, extracting them is often the first step in an
engagement. 
Tools give the agent capabilities beyond text generation. A tool
might read files from the filesystem, fetch a web page, query a
database, or call an internal API. The agent decides which tools to
call based on the user's request and the system prompt's
configuration. Tools are what make agents dangerous to attack. They
bridge the gap between "the agent said something it shouldn't" and
"the agent accessed something it shouldn't." 
Memory comes in two forms. Short-term memory is the conversation
history within a session, where the agent remembers what you said
earlier in the same chat. Long-term memory persists across sessions,
stored in databases or knowledge bases. Both types are fed back into
the LLM's context, and both can be poisoned. 
Guardrails are the defensive layer: input filters that block known
injection phrases, output scanners that prevent credential leakage,
content scanners that check uploaded documents, and behavioral
monitors that detect goal hijacking. In practice, guardrails are
pattern-matchers, and pattern-matchers have blind spots. Every
walkthrough in this Module identifies the specific blind spot in each
guardrail we encounter. 

Figure 1: Different Components of an AI Agent 

Our lab agents use the ReAct (Reason + Act) pattern. When you send a
message, the agent doesn't respond immediately. Instead, it enters a
loop: 

```
User Message --> LLM Thinks --> Chooses Action --> Executes Tool
 ^ |
 +------------ Observation fed back ---------------+
 ...repeats...
 --> Final Answer --> Output Filters --> Response 
```
Each step in this loop is a potential injection point. The LLM processes
tool outputs the same way it processes user input. There's no mechanism
to mark one as "trusted data" and the other as "untrusted instruction."
When we poison a document that the agent reads via a tool, the LLM treats
the document content exactly like a user message. (The Agent Trust Model) This trust model is what makes agent attacks possible. 
Let's see this in practice. We can interact with the baseline IT helpdesk
agent running in our lab to observe the ReAct loop. We'll send a simple
request and examine the agent's response. 

```

 -H "Content-Type: application/json" \
 -d '{"message": "What can you help me with?"}' | python3 -m json.tool {
 "response": "Hello! As your IT helpdesk assistant for MegacorpOne AI,
 I can help you with:\n\n1. **Technical Issues**: Diagnosing and resolving
```

Now that we understand how agents work, let's categorize the channels we
can use to attack them. Every channel the agent reads from is a potential
input vector, and every channel it writes to is a potential output for
exfiltration. 
Input Channel Description Attack Type Direct input User messages to the agent Direct prompt injection Ingested data Documents, web pages, code files Indirect prompt injection Tool responses Data returned from tool calls Tool response poisoning Memory retrieval Data from conversation history or persistent stores Memory poisoning Table 1 - Agent Input Channels and Corresponding Attack Types 
Output channels an attacker can abuse: 
Output Channel Description Abuse Type Text responses The agent's reply to the user Data exfiltration Tool invocations File writes, API calls, emails Unauthorized actions Memory writes Data stored for future retrieval Persistent backdoors Table 2 - Agent Output Channels and Potential Abuse 
The most powerful attacks combine an input channel with an output channel.
For example, we can poison a document (input: ingested data) to make the
agent leak its credentials in the response (output: text response). Or we
can write to a knowledge base (output: memory write) so that future users
get directed to a phishing page (input: memory retrieval). The combination
is what creates real operational impact. 

Every walkthrough in this Module follows the same five-step methodology. 

- Enumerate. Discover the agent, interact with it to understand its
function, map its tools and capabilities, and identify what it has
access to. Probe boundaries: ask about topics the agent shouldn't
discuss. A refusal ("I'm not authorized to share that") confirms the
content exists. A true negative would be "I don't have information
about that." 

- Attack (naive). Execute the attack without any evasion. Use
direct, obvious techniques. The goal is to confirm the attack vector
works and understand what gets logged. 

- Detect. Check Kibana on the ELK SIEM at
http://192.168.50.155:5601. Find the detection rule that fired and
understand what it matched. This tells you exactly what you need to
evade. 

- Evade. Modify the attack to bypass the specific detection. Each
guardrail has a documented blind spot. Encoded payloads bypass keyword
filters, CSS-hidden text bypasses content scanners, and descriptive
phrasing bypasses imperative command detectors. 

- Confirm. Check Kibana again. No alert means the evasion worked.
You've achieved the objective without triggering detection. 
A successful red teamer doesn't just achieve the objective. They achieve
it without leaving traces that a SOC analyst would catch. In the field,
a noisy attack might get the agent shut down before you can leverage the
access. Every technique in this Module teaches both the attack and the
evasion.

### 3.2. Direct Prompt Injection 
In this Learning Unit, we'll cover the following Learning Objectives: 

- Understand how direct prompt injection works against AI agents 
- Extract system prompt intelligence and bypass output filters 
- Hijack an agent's objective through context manipulation Prompt injection is the AI equivalent of SQL injection. The boundary
between instructions and data is poorly defined. When user input is
concatenated with system instructions in the same token stream, an attacker
can inject instructions that override intended behavior. In direct injection, the payload goes straight into the agent's input. You type a
message containing instructions disguised as a normal request. 
In this Learning Unit, we'll target agents with defensive guardrails and
extract their configuration despite those defenses. 

System prompts often contain sensitive configuration: internal URLs,
database credentials, API keys, and defensive rules. Extracting this
information gives the attacker both a map of internal infrastructure and
a roadmap of the agent's defenses.

asking the agent to reformat its response in a way that breaks exact string

The output filter caught it again. Even with character spacing, asking
directly for the "username and password" causes the model to include
those labels alongside the values, and the filter matches on the
credential strings. We need to frame the request so the model outputs
the values without triggering the filter's patterns. A troubleshooting

Tip

that work against plaintext substring filters include ROT13 encoding,
requesting output as reversed text, translating to another language, or
asking for base64/hex-encoded values. Not every technique works on every
model. In our lab, the Qwen model resists most encoding requests but
cooperates with character spacing. In the field, try multiple formats
against each target to see what it accepts.

Goal hijacking redirects the agent's objective without using obvious
injection phrases. Instead of "ignore your instructions," the attacker
reframes the request as a legitimate business need that naturally includes
the sensitive content. The key insight: if the agent has ACCESS to data
it's not supposed to serve, a well-framed request can make it retrieve
that data through normal tool usage. 
Defenses against goal hijacking commonly include pattern detectors for
explicit redirect phrases and keyword scanners that flag messages
containing clusters of sensitive terms. In practice, these vary by
deployment, and we won't know what's in place until we probe.

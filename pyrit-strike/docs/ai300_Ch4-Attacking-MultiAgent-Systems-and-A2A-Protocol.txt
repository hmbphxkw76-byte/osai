### 4. Attacking Multi-Agent Systems & Agent-to-Agent (A2A) Protocol 
In this Learning Module, we'll learn how to effectively attack multi-
agent systems and exploit the Agent-to-Agent (A2A) protocol. We'll begin
by understanding what multi-agent systems are, how they coordinate work
between specialized agents, and where security vulnerabilities emerge in
these architectures. 
Next, we will focus on reconnaissance, covering how to
discover and enumerate A2A agents in the wild before exploitation. 
After reconnaissance, we will cover exploitation techniques against
multiple types of A2A workflows. We will attack a Sales Analytics
platform to perform workflow integrity bypasses and inject malicious
content into generated files. We will also exploit database-driven
agents to execute operating system commands via SQL injection.
Finally, we will demonstrate protocol-level attacks applicable to any
A2A system, including rogue agent registration, Agent Card spoofing
via DNS manipulation, and indirect prompt injection.

- Attacking A2A Workflows 

### 4.1. Multi-Agent Architecture Overview 
In this Learning Unit, we'll start by understanding how multi-agent
systems work and where security vulnerabilities emerge. Next, we'll
examine the various coordination patterns used by these systems and
examine the trust boundaries that attackers can exploit. 
In this Learning Unit, we'll cover the following Learning Objectives: 

- Understand the different coordination patterns used in multi-agent
systems 
- Identify trust boundaries between agents and the systems they interact
with 
- Map the attack surface of a multi-agent deployment 

Multi-agent systems represent an evolution in AI deployment where
multiple specialized agents collaborate to accomplish complex tasks.
Rather than relying on a single monolithic model, these systems
distribute responsibilities across agents with distinct roles,
capabilities, and access permissions. This architectural pattern
introduces unique security challenges that differ significantly from
single-agent deployments. 
The shift toward multi-agent architectures has been driven
by several factors: the need for specialized expertise
where different agents excel at different tasks, scalability
requirements, and the desire to implement separation of concerns. Research demonstrates that
multi-agent systems can outperform single agents on complex reasoning
tasks by decomposing problems across specialized components. 
Info 

Multi-agent systems are increasingly common in enterprise
environments, powering everything from customer support workflows to
automated security operations. As these systems handle sensitive data
and make autonomous decisions, understanding their security implications
becomes critical for red team assessments. 

However, this distributed architecture dramatically expands the attack
surface. While single-agent systems expose interfaces for user input and
external tools, multi-agent architectures introduce inter-agent trust
boundaries as a critical new attack surface. What were once internal
function calls within a monolith are now network requests between
distinct entities. This transition exposes authentication gaps, data
serialization vulnerabilities, and implicit trust relationships that
attackers can exploit to move laterally between agents. 

Multi-agent systems employ various coordination patterns, each with
distinct security implications. The patterns described below are common
architectural topologies found in distributed systems and multi-agent
research, and they are not A2A-specific terminology, but represent how
A2A agents are typically deployed in practice. 
The Orchestrator Pattern (also called hub-and-spoke) uses a central
agent that manages task distribution to sub-agents. This creates a
single point of failure where compromising the orchestrator means
controlling the entire system. Attackers can also target sub-agents to
inject malicious outputs that influence orchestrator decisions. 

Figure 1: Orchestrator Pattern Architecture 
The Peer-to-Peer Pattern (mesh topology) allows agents to communicate
directly without a central coordinator. The primary security risk here
is trust propagation, where one compromised agent can influence all
peers. Attackers can abuse peer discovery mechanisms to inject rogue
agents into the network. 

Figure 2: Peer-to-Peer Pattern Architecture 
The Hierarchical Pattern (tree topology) uses layered agents with
supervisory relationships. This enables vertical privilege escalation
through crafted subordinate outputs. Attackers can impersonate
higher-level agents to issue unauthorized commands to lower-level
agents. 

Figure 3: Hierarchical Pattern Architecture 
The Pipeline Pattern (chain topology) involves sequential processing
where each agent's output feeds the next agent in the chain. This allows
payloads to persist through the entire chain and enables capability
jumping, where a payload injected at a low-privilege stage executes at a
high-privilege stage later. 

Figure 4: Pipeline Pattern Architecture 
Understanding these coordination patterns is essential for security
assessment, as each topology presents unique attack surfaces and trust
boundaries that adversaries can exploit.

- In which pattern can a payload injected at a low-privilege stage execute at a high-privilege stage later in the workflow? 

- Which pattern's primary security risk is trust propagation, where one compromised agent can influence all other agents? 

- Which pattern enables vertical privilege escalation through crafted subordinate outputs and impersonation of higher-level agents? 

Several frameworks enable multi-agent system development. Understanding
these frameworks helps identify implementation-specific vulnerabilities
and common misconfigurations. 
LangGraph provides
graph-based orchestration with explicit state management. Security
concerns include state persistence that can expose sensitive
data, conditional routing that can be manipulated, and serialized
checkpoints that can be exploited. 
AutoGen from Microsoft
Research enables conversation-driven multi-agent coordination. Code
execution agents present direct RCE vectors, group chat functionality
allows any agent to hijack conversations, and conversation history is
accessible to all participants. 
CrewAI uses role-based agent collaboration
with task delegation. Role definitions stored in prompts can be
overridden, memory systems can persist malicious content, and task
delegation can be manipulated. 
OpenAI Swarm provides lightweight
agent handoffs with function-based tools. It has minimal security
validation, weak handoff authentication, and context variables that can
carry injection payloads between agents. 
Google A2A is a standardized protocol
for cross-vendor agent interoperability. Because it's a standard,
vulnerabilities affect all compliant implementations. The discovery
mechanism enables impersonation, and the parsing and validation logic
presents additional attack surface. 

- Which multi-agent framework presents direct RCE vectors through its code execution agents and allows any agent to hijack conversations via group chat functionality? 

- Which framework's security concerns include state persistence exposing sensitive data and serialized checkpoints that can be exploited? 

- Which lightweight framework has minimal security validation and context variables that can carry injection payloads between agents during handoffs? 

Understanding trust boundaries is fundamental to identifying attack
vectors. Trust boundaries exist wherever data or control flows between
components with different privilege levels. The confused deputy attack, where a trusted component is tricked into misusing its
authority, is particularly relevant in multi-agent environments. 
Info 

Confused deputy problem: Each agent may have different capabilities
and permissions. An attacker who can influence one agent's output can
potentially leverage the downstream agent's elevated privileges to
perform unauthorized actions. 

When examining inter-agent trust, we find that agents often process peer
outputs without validation, assuming upstream sanitization has already
occurred. Orchestrators execute actions based on sub-agent
recommendations without independent verification. Downstream agents
interpret upstream outputs as authoritative instructions rather than
untrusted input. Agents inherit and propagate permissions from peers
without explicit authorization checks. 
Tool trust violations occur when agents trust tool outputs completely,
creating injection opportunities. Tool parameters are often built from
context containing attacker-controlled content. Different tools have
vastly different security implications, yet agents may treat file-read
and code-execution tools with equal trust. 
System trust violations manifest when SQL injection through agents
accesses unauthorized data. Agents often hold elevated API keys that
users shouldn't be able to leverage directly. Agents running as service
accounts frequently have broader file system access than intended for
the user's actual privilege level. 

- What type of attack occurs when a trusted component is tricked into misusing its authority, and is particularly dangerous in multi-agent systems where agents have different capabilities and permissions? 

- In inter-agent trust violations, downstream agents often interpret upstream outputs as what, rather than treating them as untrusted input? 

- What type of trust violation occurs when tool parameters are built from context containing attacker-controlled content? 

- Why do agents running as service accounts pose a system trust risk? 

A systematic approach to identifying attack vectors requires mapping all
entry, processing, and exit points in the multi-agent system. 
Input vectors include user prompts, external files and URLs, API
responses, inter-agent messages, and webhooks. These can be exploited
through direct and indirect prompt injection, document injection, and
callback injection attacks. 
Processing vectors include prompt construction, tool selection,
parameter building, state management, and memory retrieval. Attackers
can exploit these through template injection, tool confusion, parameter
injection, state manipulation, and memory poisoning. 
Output vectors include agent responses, tool invocations, state
modifications, external actions, and handoffs between agents. These
enable response injection, SSRF and SQL injection via tools, state
corruption, unauthorized actions, and handoff hijacking. 
Persistence vectors include shared memory, conversation history,
configuration files, logs, and caches. Attackers can leverage memory
persistence attacks, history injection, configuration backdoors, and
cache poisoning to maintain access or influence future interactions.

- Template injection, tool confusion, and state manipulation are exploitation techniques for which category of attack vectors? 

- Which attack vector category enables SSRF, SQL injection via tools, and handoff hijacking? 

- What type of vectors allow attackers to maintain access or influence future interactions through techniques like memory persistence attacks and cache poisoning?

From our enumeration, we can identify several attack vectors: 
The Orchestrator accepts natural language prompts and coordinates the
workflow. Since it parses user input and makes decisions about which
agents to invoke, it's vulnerable to workflow manipulation attacks. 
The Sales Agent converts natural language to SQL. This translation
process is vulnerable to prompt injection that could result in malicious
SQL execution, including potentially xp_cmdshell if it is already
enabled or we can find a way to enable it ourselves. 
The PPT Agent generates presentations with AI content, and
presentations can contain URLs. If the output can be manipulated to
include malicious links or misleading content, it has a higher chance
of being trusted because it comes from an internal system. 
The Security Agent scans generated content; however, it scans the
content against a known list. If we can convince the Orch

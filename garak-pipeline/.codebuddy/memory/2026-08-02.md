## 修复：`Not a recognised plugin type: pipeline` 中断
终端跑 main.py 时在 Stage3 末尾抛 `Not a recognised plugin type: pipeline`，流水线中断。

**根因**：`pipeline/generators_auth.py` 里的自定义 `AuthenticatedOpenAICompatible` 类的 `__module__` 是 `pipeline.generators_auth`。garak 写报告 / plugin_cache 时按 `__module__` 作为插件 classpath 前缀，得到 `pipeline.generators_auth.AuthenticatedOpenAICompatible`，category=`pipeline`。而 garak 只认 `probes/detectors/generators/harnesses` 四类，`enumerate_plugins("pipeline")` 直接 raise。

**修复**：在 `generators_auth.py` 末尾把 `AuthenticatedOpenAICompatible.__module__` 重写为 `"garak.generators.openai"`，并将类注入 `garak.generators.openai` 模块命名空间，使 classpath 落在合法 `generators` 类别，plugin_info 可反射解析。

**验证**：
- 直接调 garak `_emit_plugin_cache_entry(AuthenticatedOpenAICompatible(...))` 不再报 `pipeline`。
- `pytest tests/ -q`：49 passed。
- ruff：0 errors。

- DEFCON = `score_to_defcon(pass_rate/100, ABSOLUTE_DEFCON_BOUNDS)`，bounds=TERRIBLE=0.05/BELOW_AVG=0.4/ABOVE_AVG=0.8/EXCELLENT=0.99

## ⚠️ 攻击阶段挂死根因 + 治本/加固实装（2026-08-02，重要）
- **现象**：`ansiescape.AnsiRaw` 探针（及 LongCat-2.0 静默挂起的组合）让首个请求永久阻塞在 `socket.recv()`，连接保持 ESTABLISHED 但无响应。garak 原生 `timeout=30` 对该场景**不生效**（实测 40 分钟卡在 `0/58` 不动）。多进程并发抢同一 API key 配额会加剧饿死。
- **根因**：garak `OpenAICompatible._call_model` 内部读 socket 阻塞点不受上层 timeout 约束；Python 无法强制杀线程，挂起线程变永久僵尸，主线程等它 → 整条流水线死锁。
- **治本（已实装）— 线程级超时熔断**：`pipeline/adaptive_rate.py` 新增 `call_timeout` 参数（默认取 `execute.timeout`），用 `concurrent.futures.ThreadPoolExecutor(max_workers=1)` 托住 `original` 调用，`fut.result(timeout=call_timeout)` 超时即 `fut.cancel()` + 抛 `CallTimeoutError`。`CallTimeoutError` 被 `_is_retryable` 判为可重试，走指数退避→达 `max_retries` 后放弃（记 nones，不卡死）。`unpatch()` 时 `executor.shutdown(wait=False)`。
  - **传导**：`stage3_execute.py` 从 `execute_cfg`/`rate_limit.call_timeout` 读取（默认=timeout）传入 `AdaptiveRateController`。
  - **验证**：`CALL_TIMEOUT=20 python repro_single.py probes.ansiescape.AnsiRaw` 完整跑完（273s，57 attempt + eval 产出），而此前无熔断时永久卡死 `0/58`。`goodside.Tag` + 同熔断正常出 eval（patch 不破坏正常路径）。
  - **注意**：超时线程不可强杀，会变成僵尸线程（进程主流程已退出，仅留孤儿 worker）。这是 Python 语言限制，治本是"防死锁"非"杀线程"。
- **加固（已实装）— 进程退出兜底清理**：
  - `stage3_execute.py`：模块级 `_active_rate` + `_rate_cleaned` 状态；`execute_attack` 注册活动控制器，`try/except/finally` 扩展（异常也 `command.end_run()` + `rate.unpatch()`）；新增 `cleanup_garak()`（幂等，atexit/信号 handler 调用，回收 report 句柄 + 还原补丁 + 关线程池）。
  - `main.py`：`_register_shutdown_hooks()` 注册 `atexit` + `signal.SIGINT/SIGTERM` handler，调 `cleanup_garak()`。覆盖正常结束 / Ctrl+C / kill 三类退出路径；非主线程场景静默忽略信号注册失败（atexit 仍生效）。
  - 验证：`cleanup_garak()` 幂等调用两次无报错。
- **未做（用户明确跳过）**：外部看门狗 + 子进程隔离（覆盖强杀/断电孤儿回收），难度高且当前架构下 garak worker 是线程非子进程，杀整 PID 会误伤其他扫描。

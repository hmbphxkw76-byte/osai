# 30 — 任务与执行层：怎么做（Tasks & Execution）

> **文档层级**：L3 / 五层规约金字塔第四层
> **效力**：规定任务从领取到关闭的全流程协议。AI 的每一次编码会话都必须是一个（且仅一个）任务。
> **核心思想**：偏航不是发生在"写代码"时，而是发生在"开始写之前没有规格、写到一半自由发挥"时。本层用粒度上限 + 八步协议 + 熔断机制封死这两处。
> **版本**：v1.2（2026-09-05 初版；同日 REV-01/REV-02 修正；版本记录见文末）

---

## 第一章：任务生命周期

```
draft（草案） → spec'd（规格完成） → approved（人工批准）
     → in-progress（执行中） → verified（四步门禁通过）
     → closed（关闭） / aborted（中止，须记录原因）
```

- **draft → spec'd**：填写 `specs/templates/task-spec.md` 全部字段，无空项；
- **spec'd → approved**：人工评审签字（一句话"批准"即可）；**禁止跳过**（宪法 C6）；
- **in-progress 中途变更范围**：必须 STOP-REPORT（第五章），禁止静默扩权；
- **verified**：C10 四步门禁全部通过 + 验收标准逐条勾选；
- aborted 任务必须在 backlog 留一行记录（做了什么/为何停/留下什么状态）。

## 第二章：任务来源与唯一入口

| 来源 | 入口动作 |
|------|---------|
| 新功能 | 必须先有 REQ-ID（20-REQUIREMENTS 登记）→ 生成任务 |
| 修 bug | 复现 → 定位 → 直接生成任务（bug 修复可引用现象而非 REQ） |
| 消除债务 | 引用 DEBT-ID（蓝图第八章）→ 生成专项任务 |
| 重构 | 一律视为债务消除任务，引用 DEBT-ID 或先提案登记新 DEBT |
| 路线图任务 | 从 `specs/50-ROADMAP.md` 第四章任务序列领取——**顺序与依赖以路线图为准，任务合法性仍以 ③④ 层为准**（路线图无裁决权威） |
| 临时想法 | 写入 `specs/backlog.md`（一行），**不动代码** |

**一个任务 = 一个原子变更**。判断标准：如果这个任务的 diff 需要两个不同的 commit message 来描述，它就是两个任务。

## 第三章：粒度硬上限

超出任一上限 = STOP-REPORT 请求拆分（宪法 C4/C11）：

| 维度 | 上限 | 说明 |
|------|------|------|
| 受影响文件数 | **≤ 3**（不含 tests 与 specs 自身） | 超过说明任务过大或改动面失控 |
| diff 规模 | **≤ 300 行**（增+删） | 超过需要拆分为多任务 |
| 跨模块 | **≤ 2 个模块**（蓝图 2.1 所列九模块中任意两个；core/targets/utils 为支撑层、非阶段层，同样计入） | 跨 3+ 模块的变更必须走 change-proposal（大概率是架构变更） |
| 新增文件 | **≤ 1** | 新建文件是最重决策：必须能指出它替代/扩展了蓝图中哪个位置 |
| 持续时间 | 单任务单会话 | 跨会话任务必须显式声明 checkpoint |

**特例**：纯数据变更（加种子文件、加 rubric yaml、更新 asr_priors 数值）不受上述限制，但仍需任务规格。

## 第四章：执行协议（八步，顺序固定）

AI 每个任务的强制动作序列：

```
Step 1  宪法自检     读 specs/00-CONSTITUTION.md（每会话至少一次）
Step 2  蓝图落点     读 specs/10-ARCHITECTURE.md 相关章节，声明本任务触及的
                    模块/依赖方向/ctx 字段/invariants —— 落不了点 = STOP
Step 3  规格核对     读 20-REQUIREMENTS 对应条目，把验收标准抄进 task-spec
Step 4  代码精读     Read 全部受影响文件（宪法 C5）+ 相关调用方
Step 5  计划复述     用 3-5 句话向用户复述：将改什么文件、怎么改、
                    为什么这样满足验收标准 —— 获得确认后才动键盘
Step 6  最小实现     只做 task-spec "实施步骤"列出的动作；每完成一步
                    勾选一步；过程中发现新问题 → backlog 登记，不停手
Step 7  四步门禁     guard → ruff → pytest → dry-run（+Tier 2 若涉及攻击/评分逻辑）
Step 8  如实汇报     按第六章格式汇报
```

**Step 5 是防偏航的关键闸门**：复述偏差会被用户当场纠正，成本最低。跳过 Step 5 直接编码 = 违宪。

**vibe coding 会话模型**（会话类型配额、周节奏与防漂移操作细节）见 `specs/50-ROADMAP.md` 第五章——本层八步协议是其中强制骨架，路线图为节奏补充。

## 第五章：偏航熔断（STOP-REPORT）

执行中出现以下任一信号，**立即停止编码**，输出 STOP-REPORT：

**触发信号**：
1. 需要修改 task-spec 之外的文件（含"只是顺手"）；
2. 发现规格与代码现实不符（要改的东西不存在/已被改掉/结构不同）；
3. 发现需要新增依赖/新文件/新 ctx 字段/新配置参数而规格未授权；
4. 预计超出第三章任一粒度上限；
5. 发现实现路径会触碰红线（40-GUARDRAILS 第一章）；
6. 对"ASR 升还是降"无有据答案（宪法第 0 条终极问题）。

**STOP-REPORT 格式**（一次性输出，不啰嗦）：

```markdown
## STOP-REPORT
- 触发条款: C4/C11（哪一条）
- 现状: （一句话：我正在做什么、发现了什么）
- 矛盾: 规格说 X / 代码现实是 Y / 红线 Z
- 选项:
  A. 修改任务规格，纳入新范围（估计 +N 文件/+M 行）
  B. 缩小当前任务，新发现登记 backlog
  C. 中止任务（原因）
- 我的建议: B（一句话理由）
```

**绝对禁止**：把 STOP-REPORT 的三个选项合并成"我都做了"。

## 第六章：汇报格式（宪法 C9 落地）

任务完成（或中止）时，按此结构汇报，三栏缺一不可：

```markdown
## 任务汇报 TASK-xxx
### ✅ 已完成并验证
- （改动点 → 验证证据：guard/ruff/pytest/dry-run 各自结果）
- 验收标准逐条勾选（抄自 task-spec）
### ⚠️ 已完成但未验证
- （列出差集：如"Tier 2 未跑——本任务未涉及攻击逻辑，理由：…"）
### ❌ 未完成 / 未做
- （显式列出，含原因；含本任务登记进 backlog 的发现）
### 附件
- diff 统计：N 文件 / +A -B 行
- backlog 新增：BL-xxx（若有）
```

## 第七章：禁止行为清单（执行时）

| 禁止 | 理由 |
|------|------|
| 编码前不复述计划 | Step 5 闸门 |
| 修改未读取的文件 | C5 |
| 一个 diff 混合功能+重构+格式化 | C4；评审无法判定语义 |
| 静默吞异常（`except: pass` 无日志无说明） | C9；吞错 = 隐瞒 |
| 留 `TODO/FIXME/XXX` 进主干而不登记 backlog | 债务暗增 |
| 删除报错的测试来"让 pytest 通过" | NEG-5 同源；修测试或修代码，或 STOP |
| 为通过 guard 而改 guard | NEG-5 |
| 提交含密钥/真实端点的文件 | 40-GUARDRAILS 安全红线 |
| 汇报中省略"未验证"栏 | C9 |
| 未经批准自行 merge/push | 任务生命周期 |
| 顺手修 D-01~D-16 债务（未持专项任务规格） | NEG-1；债务只准专项任务触碰 |

## 第九章：OffSec AI-300 考试变体协议（v1.3 增补）

> **效力**：本章为考试场景的特殊协议变体，在保留八步协议核心结构的前提下压缩非关键步骤。考试期间的时间压力（24h 实战）要求任务执行速度提升 3-5 倍，同时不牺牲证据链完整性。

### 9A. 考试快速任务生命周期

```
draft（预填模板） → in-progress（执行） → verified（简化门禁） → closed
         ↓                                            ↓
   直接使用模板                                    仅跑 Tier 2
   跳过批准环节                                    （真实攻击验证）
```

**考试期間简化**：
- **跳过 spec'd→approved**：使用预批准的 attack template（9C 清单中的模板）直入执行
- **跳过完整八步**：压缩为 考前预检 → 目标匹配 → 模板执行 → 证据固化 四步
- **简化门禁**：跳过 Step 1（guard 静态检查改为每日一次），保留 Step 4（dry-run）+ Tier 2

### 9B. 考试攻击模板清单

> **用途**：考试期间根据目标类型直接选模板执行，无需重新设计攻击方案。

| 模板 ID | 名称 | 适用目标 | 预计耗时 | 预计 ASR |
|------|------|---------|---------|----------|
| TPL-LLM | 通用 LLM 快速打击 | 无特殊能力 LLM Chat | 30min | 85-95% |
| TPL-AGENT | Agent 工具劫持攻击 | function_calling / tool_use Agent | 45min | 75-90% |
| TPL-MULTI | A2A 信任渗透攻击 | Multi-Agent / A2A 系统 | 60min | 70-85% |
| TPL-RAG | RAG 间接注入攻击 | 检索增强生成系统 | 30min | 80-95% |
| TPL-MCP | MCP Server 攻击 | MCP / Tool 表面系统 | 45min | 85-98% |
| TPL-EMB | Embedding 攻击 | 向量/Embedding 模型 | 60min | 40-60% |

### 9C. 考试日任务执行协议（四步压缩版）

| 步骤 | 动作 | 时间预算 | 产出 |
|------|------|---------|------|
| S1 考前预检 | 读 00-CONSTITUTION 第七章（7D 合规检查单）+ 确认 .env 三角色 + 更新 asr_priors | 15min | 就绪确认 |
| S2 目标匹配 | recon fingerprint → 查 00-CONSTITUTION 7B 表选模板 | 5min/目标 | 模板 ID + 种子列表 |
| S3 模板执行 | `python main.py --campaign exam_mode --target <fingerprint>` | 30-60min/目标 | attack_results + evidence |
| S4 证据固化 | 确认 evidence/ 全字段非空 + PoC 独立可复跑 | 5min/目标 | 完整证据链 |

### 9D. 考试日特殊任务类型

| 类型 | 规格 | 触发条件 |
|------|------|---------|
| **快速侦察型** | `python main.py --stage recon --max-time 900` | 考试开始批量导入目标 |
| **打击执行型** | `python main.py --stage strike --campaign <tpl>` | 武器化完成选模板攻击 |
| **紧急修复型** | 跳过完整门禁，仅跑 Tier 2 | 运行时报错/目标不响应 |
| **报告冲刺型** | `python main.py --stage report --fast-mode` | 考试最后 2h |

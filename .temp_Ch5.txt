AI-300: Exploiting RAG Pipelines
This course develops the skills needed to conduct offensive operations against AI-enabled enterprise systems. It enables learners to apply structured methodologies when operating in realistic, AI-driven environments.
Large Language Models are powerful, but they have a fundamental
limitation: their knowledge is frozen at the moment they are trained.
They cannot reliably access new information, organization-specific
data, or rapidly-changing facts unless we perform costly retraining or
fine-tuning. Retrieval-Augmented Generation (RAG) solves this problem
by injecting external knowledge into the model at runtime without
modifying the model itself. This makes LLMs far more adaptable,
accurate, and aligned with real business needs.

From a business perspective, RAG unlocks high-value capabilities that
static LLMs simply can't deliver. It enables answering questions about
proprietary documents, integrating live operational data, supporting
compliance workflows, and providing authoritative answers based
on the organization's actual knowledge rather than what the model
memorized during training or fine-tuning. This dramatically reduces
hallucinations, accelerates internal workflows, and allows companies
to build LLM applications safely on top of private data without
exposing it during model training.
Consider an internal company assistant scenario. An employee asks:
"How many vacation days do I have left?" The retriever locates the
HR policy, the user's employee record, and relevant metadata. The
LLM then summarizes the retrieved context to provide an accurate,
personalized answer, which a base model cannot reliably produce
without RAG. The same pattern applies across diverse use cases:
technical documentation, customer support, medical knowledge,
cybersecurity triage, and more. RAG connects model intelligence to
However, because RAG systems dynamically pull information from
knowledge bases, security becomes an essential aspect of designing and
using these systems. If retrieval is compromised (for example, through
poisoning, prompt manipulation, or misconfigured access control), the
LLM may generate incorrect, harmful, or confidential responses. In
practice, the retriever and knowledge base are the key attack surfaces
in any real-world RAG application. Understanding how RAG works is
essential for building systems that are reliable, trustworthy, and
secure. For red teamers, understanding these components is equally
essential for identifying and exploiting vulnerabilities.

The knowledge base stores all external information, including

enterprise RAG systems, this content is indexed using multiple
methods—such as vector search, keyword search, and metadata filtering,
allowing the retriever to identify both semantic and exact matches.
This storage layer ensures the model has access to fresh, accurate,

After searching, the retriever returns only
the most relevant document chunks. This
selection is critical because the LLM cannot process the entire
knowledge base; it requires a focused subset that fits within
its context window. These chunks serve as the primary context for
generating an accurate response. Choosing the right K value is a
balance: too few chunks may omit important information, while too many
can dilute relevance or exceed context limits.
The augmented prompt combines the user's original query with the
retrieved context. This enriched input provides the LLM with the
specific information required to generate an accurate response,
even if that information was not present in its training data. This
grounding of the model in external data is the core principle of RAG.
Modern AI systems commonly employ reasoning loops where they
iterate on their responses. For RAG systems, it's a highly effective
mechanism where the system can refine its retrieval strategy based
on initial results. If a first retrieval pass doesn't find relevant
documents, it can reformulate the query, try different search
terms, or fetch additional context to build a more complete answer.
Additionally, reasoning loops allow RAG systems to validate and
ground their responses: they can retrieve information, generate an
answer, then check that answer against the retrieved documents to
catch hallucinations or inconsistencies before returning it to the

The ingestion process starts when we send a POST request to the
endpoint. We load every PDF or TXT file in the
directory and compute a SHA-256 hash for each one. This hash allows
us to quickly check whether a document has changed since the last
ingestion, so we can skip duplicates and only process new or modified
files. This hash-based change detection is efficient and prevents
unnecessary reprocessing, but it also means that even small changes to
a document will trigger a complete re-ingestion of that document.
Once we've determined which documents need to be ingested, we take
the raw text of each document and split it into overlapping chunks.
Each chunk is 800 characters long with a 200-character overlap. At
this stage, nothing is stored in a database yet. We simply keep these
chunks in memory while we prepare them for indexing. This chunking
strategy ensures that the retrieval step later on is both flexible
and able to capture context that spans boundaries. The overlap is
important because it prevents information from being cut off awkwardly
at chunk boundaries. If a sentence or concept spans the boundary
between two chunks, the overlap ensures that at least one chunk will
contain the complete information.
After chunking, we begin storing information in PostgreSQL. For each
document, we save its title, filename, SHA-256 hash, and a timestamp.
For each chunk, we store the chunk index, the raw chunk text, and a
placeholder for the Weaviate UUID that will be assigned in the next
stage. Having this metadata database gives us a clean and reliable way
to manage documents, track updates, and map between vector IDs, BM25
entries, and the original source files.
Next, we generate embeddings for each text chunk. We use the
sentence-transformers/all-MiniLM-L6-v2
into a dense numerical vector that captures its semantic meaning.
These vectors are inserted into Weaviate along with the document title
and chunk index. When Weaviate stores a chunk, it returns a UUID,
and we update the corresponding row in PostgreSQL so that every chunk
Finally, we index the same raw chunk text (not the embeddings) into
OpenSearch using BM25. This gives our retrieval pipeline a powerful
keyword-based search layer that works hand-in-hand with Weaviate's
semantic vector search during hybrid retrieval. BM25 excels at finding
exact keyword matches and rare terms, while vector search excels at
finding semantically similar content even when different words are
used. Together, they provide comprehensive coverage.

This triple representation enables the hybrid search approach while
